## 发生了什么

| 项 | 值 |
|---|---|
| 保留正向样本 | 40756（0–41.003 s） |
| 缺口位置 | 期望序号 40756，实际收到 40760 |
| 缺口大小 | 恰好 4 个样本（一个完整数据页） |
| 固件记录环 dropped | **0** |
| 主机请求/应答 | sent 2450 / replies **2449**（一次无应答） |
| 主机重试次数 | 0 |
| 帧解码拒绝数 | **0** |
| 固件结束状态 | state=4（终止），reason=1（本机取消） |
| 撤权核对 | source=none，authority=false，manual_stop=false |

解码整份 wire.jsonl 后确认：缺口正好是一个未被应答的整页，固件侧记录环没有丢样、串口帧也没有 CRC 或转义损坏。**所以原因是主机侧丢失了一次应答，主机读到了后面那一页，而非固件缓存溢出或电机/通信动作异常。**

精确复核该处的数据页序列：

```text
页号 10187: first_sequence=40748  count=4  dropped=0
页号 10188: first_sequence=40752  count=4  dropped=0
页号 10189: first_sequence=40760  count=4  dropped=0   <-- 缺 40756 那一页
页号 10190: first_sequence=40764  count=4  dropped=0
```

- 缺失页为 40756（4 个样本），此后各页序号连续。
- 相邻页间隔 3.29 ms（其余页约 5–6 ms），不是长时间停顿。
- 全部 10194 页 `dropped=0`，解码器拒绝计数为 0，说明没有 CRC/转义错帧。
- 主机发送 2450 帧、收到 2449 个应答，正好少一个应答，与该缺失页对应。


脚本按既有规则在序号缺口处停止："高频记录身份/序号缺口; 已有文件保留, 不重做动作"。这符合原设计，没有为凑数据而放宽判据。
