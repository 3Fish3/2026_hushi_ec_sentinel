# 应用装配与接入指南

本文面向"要写机器人应用层"的开发者: 从零开始把设备、控制、输入、授权和发送接起来.
具体到哨兵某个机构的模式选择与参数来源不在这里, 统一维护在 [哨兵 Checklist](../robots/sentinel/现有能力与待确认Checklist.md); 调参与台架操作见 [GM6020 单电机测试](GM6020单电机测试.md) 与 [串口观测与应用接入](串口观测与应用接入.md).

可运行参考: [host_single_axis.cpp](../../examples/host_single_axis.cpp) (最小单轴) 与 [host_app_example.cpp](../../examples/host_app_example.cpp) (四轮 + DM 关节 + 遥控 + IMU + 控制权 + 监控).

## 1. 组装顺序

```text
1. 设备表      每个设备的 bus / id / 协议 / 传动 / 方向 / 有效期
2. 设备对象    按设备表构造; 无效布局在初始化阶段就被拒绝
3. 轴/机构     用设备构造轴或机构对象, 指定模式、参数与目标有效期
4. 发送组      同组电机合并成一帧; 每个槽位绑定一个设备
5. 输入        遥控解码 + 输入视图 (时效与边沿); 板级完整样本经 board_inputs.hpp 交接
6. 授权        会话、控制权、执行上下文与停机策略
7. 任务        一个控制周期里按固定顺序调用
8. 监控(可选)  注册表发布 + 串口/SWD 只读后端
```

设备与轴的生命周期都由组装层持有: **轴不拥有设备**, 一个设备只属于一个轴. 对象必须在并发启动前构造完成.

## 2. 一个控制周期的固定顺序

```text
输入时效        remote.snapshot(now) / input_remote(now) / 反馈是否新鲜
来源仲裁        ControlAuthority::update(...) -> token 或空
目标换算        输入量 -> SI 单位目标 (rad/s, rad, A); 单位换算只在应用层做
逐轴执行        ExecutionContext::evaluate -> enable / set_target / tick
发送            DjiTxGroup::send(now, 每槽输出) 或设备自己的编码帧
状态回传        轴快照 + 设备状态 + (可选) 注册表记录
```

顺序不能乱: 先判许可再设目标, 先算输出再发送; **协议层只报告输入, 轴只执行结论, 发送层不做许可判断**——否则同一套故障状态机会被写三遍并且互相矛盾.

## 3. 最小单轴 (可编译函数片段)

下面的片段省略了 include 与授权/时效判断, 只展示装配与调用顺序; 完整可运行版本见 [host_single_axis.cpp](../../examples/host_single_axis.cpp).

```cpp
MemoryCan bus;                                    // 或板级 CanTx 实现
DjiDevice device{{1, DjiMode::c620_current, 1, 1, 1, {10}, 100, 16384}};
DjiAxis axis{{1.0f, {1.0f,0,0,0,-1,1}, {}, ArcMode::continuous, {10}, 10.0f, 0.02f, 0.0f}, device};
DjiTxGroup sender{bus, 1, 1, {2}, {&device, nullptr, nullptr, nullptr}};

// 每周期:
const auto grant = axis.enable(ControlMode::velocity, CommandSource::remote, authorized, ready);
axis.set_velocity(target_rad_s, now);
const auto result = axis.tick(now, dt_s);
sender.send(now, {DjiOutput{result.normalized_output.value_or(0.0f), now}, std::nullopt, std::nullopt, std::nullopt});
```

`value_or(0.0f)` 只是这个虚拟台架的选择: 实车里"无输出时发什么"是机构决策, 必须显式写出来, 不能让发送层替你决定.

## 4. 多设备装配要点

- **同组发送**: 四个槽位合并成一帧; 某个已安装槽位本周期没有新输出时整组拒绝 (`missing_output`), 不会给缺失槽位补零. 补零是应用层的停机动作.
- **混合总线**: DJI 与 DM 可以共总线, 但初始化时会核对接收 ID 归属与同总线冲突 ([bus_layout](../../include/ec/drivers/bus_layout.hpp)).
- **不同协议族**: C610/C620 可以同组; 跨协议族或跨组共享同一命令 ID 会被拒绝.
- **DM MIT**: `DmDevice::encode_mit()` 只按已配置的 `PMAX/VMAX/TMAX` 编码, 越界或非有限值返回空; 使能/失能是显式请求, 不自动 enable. `request_result()` 回答的是"期望状态当前是否满足" (由请求方向 + 新鲜反馈状态位决定), 不是本次命令的 ACK, 也不代表机械动作完成; 需要送达/完成语义时由上层协议自己配对请求与反馈.
- **停机策略**: 每个机构分别配置 `ExecutionPolicy`; 轮子通常是 `zero_output`, 位置保持类关节通常是 `hold_position`. 未配置时框架报告 `unspecified`, 不静默归零.

## 5. 状态回传

轴层: `axis.state(now)` 给出模式、使能、目标、反馈、输出与状态的一致快照, 应用不需要访问协议槽位.
设备层: `DjiDevice::state(now)` / `DmDevice::state()` 给出轴侧速度、位置与有效性.
整机监控: 把关键字段写进 [监控注册表](../modules/monitor/监控注册表.md), 由串口或 SWD 只读读取; 未实现的来源必须标 `unknown`, 不填健康零值.

## 6. 添加一个新机器人或新设备

1. 设备表: 在板级或应用目录里显式写出 bus/ID/协议/传动/方向/有效期, 不猜电调型号.
2. 协议: 已有编解码直接复用; 新协议在 `include/ec/drivers/` 下按"映射 + 命令/反馈结构 + 显式范围检查"的方式实现, 并补 golden 帧测试.
3. 轴/机构: 需要新语义时优先组合已有控制组件, 而不是复制 PID.
4. 装配: 在应用入口构造设备与机构, 配置停机策略与授权条件.
5. 验证: 主机契约测试 (可用内存总线/内存 SPI 只替换外设) → 交叉编译 → 单独授权的台架或实机步骤.

## 7. 边界提醒

- 主机示例通过不等于实机验收: 内存 CAN 的 `accepted` 只表示"帧被交给发送层".
- 不要从示例里抄走演示数值当实车参数: 参数来源与适用条件见 [GM6020 单电机测试](GM6020单电机测试.md) 与 Checklist.
- 不要为了省事让脚本直接透传 CAN 或写内存绕过授权: 仲裁、限幅与保护必须留在 MCU 侧.

## 装配层的设备所有权与链接验证 (修复后口径)

- `ec::sentinel::dji_device(i)` / `dm_device(i)` 返回**可写**指针: APP 需要用非 const 设备构造
  `DjiAxis`、设置位置参考、编码使能帧。控制策略、仲裁与发送调度仍由 APP 负责, 装配层只保证
  设备实例与接收路由的唯一性; 表为空或无效时返回空指针。
- 收帧任务每周期最多解析 `can_frames_per_cycle`(= 32, 等于接收队列容量) 帧, 剩余帧留到下一周期;
  队列自身溢出仍计入 `rx_dropped`。单周期工作量因此有硬上界, 不随总线负载增长。
- **非部署链接验证产物** `ec_link_verify`: 板级目标启用 `--gc-sections`, 源码编进静态库不等于
  被链接进镜像。该产物用静态对象与假 sink 引用各通用组件, 链接后由
  `check_link_verify.py` 核对 17 组符号是否真的在 ELF 里。它不驱动外设、不实现 APP 钩子,
  **不是可烧录固件**, 默认固件 `sentinel_s1` 的无输出审计规则不因它放宽。
- DM 使能/目标是**显式请求**: `encode_enable()` 只编码, 发送结果与设备状态都要自己看;
  示例里"发送成功"与"观察到设备使能反馈"是两个独立条件, 只有后者成立才下发 MIT 目标。
