# 电控通用核心框架架构设计

## 1. 文档边界

本文是本项目架构决策的单一维护入口, 记录已确认的范围、职责与契约及架构层待定事项. 首个哨兵的现有能力、控制行为证据与逐项待确认内容集中维护于 [哨兵能力与待确认 Checklist](robots/sentinel/现有能力与待确认Checklist.md), 本文不重复维护该清单. 参考资料是设计证据, 不自动成为已批准需求.

已获授权开始核心代码建设. 当前实现包含通用核心库 (设备与轴门面、控制与位置串级、输入与姿态估计、运动学、会话与授权、监控注册表)、主机装配示例及覆盖 S1–S4 的非运动板级测试固件, 不是整车控制固件, 也**尚未开始哨兵 APP 应用层**: 默认镜像的安装表为空、APP 钩子为弱符号空实现, 因此不存在任何执行器发送路径. 实机验收状态与逐阶段证据集中维护在 [哨兵实施与验收](robots/sentinel/实施与验收.md), 本文不重复维护验收结论, 也不代表烧录或运动试验授权. 后续应更新对应结论, 不逐轮追加会话记录或另建重复决策清单.

## 2. 交付目标与参考基线

### 已冻结

- 最终交付是通用核心框架, 保留扩展能力, 各机器人组根据实际硬件和控制需求进行适配.
- 首个落地是现有参考哨兵的硬件控制能力, 加上与上位机协商后的通信.
- 首版不提前实现其他兵种或其他平台后端.
- 旧代码仅供现有能力、硬件与必要控制行为参考. 新框架可以完全抛弃旧实现, 不要求源码复用、内部接口兼容或延续调试逻辑与硬编码策略.
- 不以“行为继承”为由保留旧实现中的安全保护缺口.

### 参考资料及适用限制

- `references/Sentinel/`: STM32F407 哨兵代码参考. 用户已确认当前工作树就是正常运行版本, 新框架使用同一套硬件, 运行事实统一见 Checklist 的 B05–B07、A07. 存在大量未提交修改, commit 本身仍不能唯一标识参考内容; 后续基线留存需覆盖工作树, 不再将运行版本是否一致作为未知项.
- `references/电控接口需求与联调建议.md`: 上下位机接口协商输入, 不是最终二进制协议. 文中的建议频率、字段和安全阈值未因引用而自动冻结.
- `references/hardware/Sentinel/`: 机械资料. 已确认存在外部依赖缺失, 详情与补交要求见 Checklist 的 I03、I07、I08. 不据此包冻结完整几何、质量、外参或运动范围.
- `references/official/`: 不同赛事规则、制作规范、裁判协议与设备手册. 参考接口资料记录目标为 2027 RMUL 3V3; 2026 规则和 2027 前瞻不得直接作为尚未公布的最终赛事常量.

机械缺件不阻塞通用核心设计, 但依赖真实参数的控制配置与实机验收不能据此宣称闭合.

## 3. 职责边界

### 已冻结

| 部分 | 职责 |
|---|---|
| 上位机 | 定位导航、视觉目标处理、运动目标生成、比赛策略与裁判规则处理 |
| 下位机 | 实时控制、执行仲裁、本地保护、设备状态与实测反馈; 不增加比赛自主策略 |
| 通用核心 | 提供可复用的驱动、控制、时间、数据交换、通信及故障监测机制 |
| 机器人适配与应用 | 选择和组装组件, 定义硬件映射、控制模式、控制权及各机构具体安全行为 |

上位机给出运动目标和许可, 不绕过下位机控制与保护直接驱动执行器. 参考代码中的按血量定时进退等比赛策略不迁入下位机通用核心.

按已认可的哨兵职责方案, 裁判系统直连 Jetson. MCU 接收必要的约束、许可及其有效性信息并落实保护, 不实现完整裁判协议转发. 具体约束消息与陈旧状态降级行为仍待协商.

核心共用的是机制与必要契约, 不强迫所有机器人使用同一种应用状态机、任务表或设备能力集合.

## 4. 平台、语言与资源

### 已冻结

- 首版使用 STM32F407 + HAL + FreeRTOS, 隔离平台依赖并保留移植边界, 暂不实现其他芯片或 RTOS 后端.
- 手写框架采用 C++, 不转向纯 C; HAL/CubeMX 等生成代码可继续使用 C.
- 初始化阶段允许动态分配; 实时控制路径不进行动态内存分配, 运行期资源有界.
- 正常控制流程不使用异常表达无消息、超时等常规结果.
- 对象关系显式, 不默认使用共享所有权或普遍引入 `shared_ptr`.
- 硬件映射、方向、传动比、控制参数与组件连接采用编译期配置及显式组装.
- 首版不交付通用运行时配置系统、参数持久化或热插拔. 调试调参能力另行限定.

手写代码采用 C++20, CMake >= 3.22 / Ninja, GNU 编译关闭异常和 RTTI. 主机侧同时使用 MinGW GCC 14.2.0 与 MSVC 验证 (两者都作为常规构建与测试目标, 不只支持其中之一); Cortex-M4F / hard-float 使用 Arm GNU 14.2.Rel1 (编译器报告 14.2.1). 手写注释使用简体中文, 厂商版权/生成代码不改写, 见根目录 AGENTS.md.

上述规则不等于已经证明 HAL、RTOS 或其他依赖全程无动态分配. 早期 F407 适配使用旧 HAL 1.8.3 / FreeRTOS 10.3.1 头文件做编译验证; S1 已独立使用 STM32CubeF4 1.28.3 中的 HAL 1.8.5 / FreeRTOS 10.3.1, 不编译旧机器人业务或 SEGGER 追踪补丁. SDK 由显式路径提供, 板级生成代码与配置纳入本仓库. S1 在调度前使用有界 heap_4 创建任务, 诊断循环不分配; 正式整车的任务与资源预算仍需落实.

S1 已按用户要求锁定本次 [ST 官方下载页](https://www.st.com/en/embedded-software/stm32cubef4.html) 对应的最新正式补丁 STM32CubeF4 1.28.3 (基础包 1.28.0), 包身份检查见 `boards/sentinel_f407/sdk.cmake`; 不跟随未固定的开发分支. 实际生成器为 CubeMX 6.18.1, 与包内 HAL/CMSIS/FreeRTOS 分别记录. 使用独立 `.ioc` 显式指定 HSE 12 MHz 为 PLL 输入, 生成 168 MHz SYSCLK、42 MHz APB1、84 MHz APB2. 手写桥接只置于 USER CODE 区, 其余逻辑在板级目录独立维护; 生成与构建约束统一见 [板级生成与构建](boards/sentinel_f407/生成与构建.md), 实机操作见 [哨兵实施与验收](robots/sentinel/实施与验收.md).

## 5. 模块与执行模型

### 已冻结

#### 5.1 显式组装与替换边界

- 不采用强制所有机器人继承的万能机器人基类.
- 平台服务和 BSP 不认识具体机器人业务.
- 电机协议驱动与控制算法分离: 驱动负责协议、设备命令和反馈; 控制组件负责 MCU 侧闭环及相关算法.
- 保留设备原生控制能力, 按实际设备选择控制模式; 不假设每种设备都支持位置、速度、力矩等相同能力.
- 通信编解码与传输分离, 协议解析不直接驱动电机.
- PID、运动学等控制组件尽量不依赖 HAL 和 RTOS, 支持针对性主机侧验证.

这些是逻辑边界, 不等于已冻结源码目录、类名或接口签名.

#### 5.2 按实时性分组调度

- 模块划分与任务划分分离, 不要求每个模块拥有独立线程.
- 模块不自行创建线程; 机器人组装层确定任务、周期、优先级和执行顺序.
- 中断只进行有界接收、时间打点和通知等工作.
- 周期任务承担仲裁、保护和控制; 通信与诊断独立于实时控制处理.
- 具体任务数量、IMU 执行方式、周期、优先级和最坏阻塞上限仍需依据设备更新率、总线预算与控制需求确定.

#### 5.3 按用途区分数据交换

| 数据用途 | 契约 |
|---|---|
| 连续运动目标 | 带有效期的最新值邮箱, 不排队执行积压旧目标 |
| 一次性动作或事件 | 有界队列, 明确队列满时的处理及重复命令语义 |
| 实测反馈和状态 | 带时间与有效性的一致快照 |

内部通道显式且类型明确, 不引入全局字符串话题总线. 同任务内允许直接调用, 不强迫所有模块交互经过邮箱; 跨任务或执行上下文的数据交接需明确同步与所有权. ISR 接收缓冲与业务事件队列是不同层次.

首批实现采用有界复制通道和显式同步策略, 不引入无锁算法或第三方消息库. 完整通道元素上限 256 字节, 事件 FIFO 容量由组装层指定, 满时拒绝新事件并返回状态. 主机以 mutex 验证一致性; F407 用保存/恢复 PRIMASK 的短临界区适配单核任务与普通 ISR, 屏蔽时延仍需板上测量. 容器不替代业务上的唯一命令来源、事件幂等或授权检查; 对象与锁必须在启动并发前组装完成.

## 6. 控制权与安全原则

### 已冻结

- 首版采用整车统一控制权, 暂不支持遥控和上位机混合控制不同机构.
- 本地保护/急停优先, 有效遥控接管优先于上位机.
- 遥控在线不等于必须占有控制权; 可通过明确模式选择授权自主运行. 遥控掉线不自动构成自主授权.
- 各机构可以单独禁用, 但首版不独立分配命令来源.
- 上位机许可不能绕过机械限位、设备故障及本地保护.
- 断链、重启或故障使相关旧运动目标和发射许可失效. 链路恢复不等于恢复执行, 必须完成重新握手、状态检查、授权与新目标下发.
- 不要求每次恢复都人工按键, 但允许自动恢复的具体条件必须另行定义. 收到任意新帧不能替代重新使能过程.
- 参数未知、未初始化、离线或零位未建立必须显式表达, 不使用猜测值允许机构执行.

“停止”“制动”“保持姿态”“失能”不等价. 各机构安全状态、故障传播范围、超时阈值及恢复条件待结合机械与控制需求逐项冻结, 不使用统一失能动作代替安全设计.

## 7. 上位机通信与物理量

### 已冻结

- 独立设计新协议, 不兼容旧的 25 字节视觉命令帧, 不实现新旧帧自动猜测切换.
- 先定义消息语义, 再协商协议版本、CRC、序号、启动标识、时间及命令有效期的具体布局与规则.
- 首版优先 UART, 传输与编解码分离; 最终端口、电平、波特率及频率需结合带宽和硬件核实.
- 控制与对外反馈采用 m、s、rad 等 SI 单位, 明确坐标系、正方向、父子关系和零位.
- 区分电机轴与关节/车轮输出轴; 设备原始量限制在驱动与诊断边界, 不将原始电流计数直接标为安培等物理量.
- 实测状态附时间与有效性. 未标定值不得冒充有效关节状态; 指令值不能冒充实测值.
- 不将内部 C++ 对象内存布局直接作为长期线协议契约.

首版通信包含命令下发、实测状态回传与必要的执行安全信息, 具体字段、刷新率、坐标系选择、接收/接受/应用反馈语义及时间同步细节仍需双方协商.

## 8. 首版哨兵交付与验证

### 已冻结的落地范围

- 四轮底盘.
- 主 yaw、发射机构 yaw、pitch.
- 摩擦轮与拨弹机构.
- 现有 MCU IMU 与遥控接入.
- 控制权仲裁、本地保护与执行状态.
- 新上位机协议及最小闭环通信, 包括实测状态回传.

不新增导航、自主比赛策略、完整裁判转发或未经确认的设备能力. 具体机构控制模式仍需逐项确认; 软件范围确认不等于机械参数和控制性能已获验证.

### 验证边界

- 实现阶段执行交叉编译及针对性主机侧行为测试, 覆盖协议、时间与过期处理、仲裁和控制换算等关键契约.
- 测试设施与风险相匹配, 不以完整物理仿真作为通用核心首版前置条件.
- 实机响应、保护触发时延、机械参数和控制参数另行验证与验收.
- 当前讨论及离线开发不授权烧录、通电运动或发弹试验.
- 编译通过与离线测试通过均不能代替实机安全和性能验收; 用户保留最终验收权.

## 9. 实现布局与后续边界

首批源码分为平台无关的 `include/ec/` + `src/` (按 `control`/`drivers`/`estimation`/`input`/`motion`/`monitor`/`transport` 分组)、F407 适配 `platform/stm32f407/`、板级静态装配 `boards/sentinel_f407/`、主机显式组装 `examples/` 和离线测试 `tests/`. 不引入万能机器人基类, 也不把 CubeMX 生成代码混入核心目录. 接入步骤见 [应用装配与接入指南](guides/应用装配与接入.md), 组件契约见 [模块使用手册](modules/README.md).

板级构建统一维护于 [生成与构建](boards/sentinel_f407/生成与构建.md), 开发阶段、软件在环边界与逐组件人工操作统一维护于 [板级实施与人工验收](robots/sentinel/实施与验收.md). 软件交付和实机验收分别推进; 硬件到位后仍从不请求执行器输出的板级基础开始, 按依赖逐组件测试, 不以仿真替代实机证据. 本文保留总体交付边界, 不重复维护操作步骤和阶段验收记录.

交付顺序:

1. 核心库、平台编译入口、主机组装与契约测试. 授权门只实现本地代次撤销; 会话、控制权与执行上下文已提供通用机制, 但机构安全状态机与停机动作仍由机器人适配层逐项定义. F407 静态库编译不等于完整固件链接或实机运行.
2. 依照哨兵已确认行为, 接入正式板级生成工程、外设收发与设备, 细化应用任务组装、执行顺序、资源及最坏执行/阻塞预算. 板级已提供静态装配入口与只读监控注册表; 安装表内容、任务与资源预算仍需随 APP 落地. 未冻结协议和控制反馈不可用猜测实现替代.
3. 完成机构控制与新协议闭环、针对性离线验证后, 另行授权实机验证与验收. 主 yaw 稳向反馈缺口保持待定, 不默认新增 IMU 或降级目标.

哨兵参考基线、硬件映射、各机构控制模式/反馈/安全行为、机械参数、时间与通信协商事项, 统一跟踪 [Checklist](robots/sentinel/现有能力与待确认Checklist.md). 这些属于已确认范围内的详细设计, 不应擅自填入推测值.

**后续实验候选, 非当前交付门槛**: 可探索物理引擎 (如 MuJoCo) 辅助云台/底盘算法验证与候选参数初调. 优先简化主 yaw → 发射 yaw → pitch 刚体模型及给定底盘旋转扰动, 后续再考虑全向轮接触. 复用正式控制与协议代码, 为质量/质心/惯量、关节与传动、执行器能力、传感器和延迟标注来源与不确定性. 不以仿真真值代替尚未确定的实车稳向反馈, 不把仿真增益直接视为最终实车参数或验收结果. 本项仅记录探索方向, 不启动引擎集成或扩大当前核心开发范围.

核心建设已获明确授权, 不表示所有哨兵待确认项已经闭合, 也不自动扩展为烧录、运动、发弹或后续代码提交/发布授权.
