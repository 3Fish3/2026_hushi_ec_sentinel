# 执行授权门 (Execution Gate)

源码: [execution_gate.hpp](../../../include/ec/execution_gate.hpp)，核心类型位于 `ec` 命名空间。对应契约测试: `tests/core_tests.cpp` 中的 `gate_and_channels`。

## 1. 为什么“一个简单的 `bool is_enabled`”是不够安全的？

很多刚接触机器人电控的同学可能会问：“要控制机器人电机能不能动，用一个全局布尔变量 `bool motor_enabled = true;` 不就行了吗？急停就设为 `false`，使能就设为 `true`。”

**在严苛的竞技机器人赛场上，这种设计极其危险！**
设想这样一个真实的事故场景：
1. 哨兵机器人在自主导航模式下全速冲刺，上位机发来一系列大转速指令。
2. 裁判系统判定掉线或操作手按下急停，系统将 `motor_enabled` 置为 `false`，电机停止。
3. 经过几秒的排查，通信恢复，操作手在遥控器上重新拨动开关使能，`motor_enabled` 重新变回 `true`。
4. **此时恐怖的事情发生了**：由于某个通信通道或驱动缓存中还残留着几秒前未消耗的冲刺指令，一旦使能瞬间恢复，旧指令被重新取出执行，机器人会突然剧烈暴冲！

**`ExecutionGate` 的核心防线：代次令牌 (Generation Grant)**
为了彻底解决这个问题，我们引入了 `Grant`（授权令牌）机制。每次系统通过安全自检并重新使能时，授权门的内部 **代次计数器（Generation）** 都会单调递增，并签发一个全新的唯一 `Grant`。
所有下发的控制指令必须绑定该时刻的 `Grant`：
- 控制器只执行持有**“当前最新代次 `Grant`”**的指令。
- 在同一授权门生命周期内，急停前签发的旧指令即使残留在缓冲区中被再次读取，其旧代次令牌也会被拒绝。跨 MCU 重启的保护还需清空旧通道并重建会话，不能只依靠本地代次。

---

## 2. 授权门不负责什么（非目标）

- **不负责全局仲裁**：授权门不直接决定“现在该听遥控器的还是听上位机的”，来源选择由顶层状态机与仲裁逻辑决定。
- **不直接驱动硬件断电**：授权门返回的是逻辑许可；当授权被撤销时，必须由应用层驱动具体机构执行相应的安全动作（如电机发零电流或闭合抱闸刹车）。

## 3. 主机可运行示例

下面的代码演示了授权门的使能、急停失效、重新使能以及对旧代次令牌的绝对拒绝：

```cpp
#include "ec/execution_gate.hpp"
#include <iostream>

// 主机可运行示例: 演示代次授权门的申领、注销与旧代次防御机制
int main() {
    // 1. 创建执行授权门对象 (每个控制链通常拥有一个独立的授权门)
    ec::ExecutionGate gate;

    // 2. 第一次使能申请:
    //    arm(控制来源, 显式授权信号, 本地自检就绪信号)
    //    参数说明:
    //    - ec::CommandSource::host: 本轮控制权授予上位机
    //    - explicitly_authorized: true (操作手通过遥控开关或协议完成了显式使能动作)
    //    - locally_ready: true (本地电机在线、传感器自检全部通过)
    const auto old_grant = gate.arm(ec::CommandSource::host, true, true);

    // 校验第一次授权是否成功获取且被当前门接受
    if (!old_grant || !gate.accepts(*old_grant)) {
        return 1; // 首次授权失败
    }

    // 3. 模拟突发异常，触发紧急熔断注销:
    //    invalidate() 会立即注销当前权限，并将内部代次号 (Generation) 单调递增 +1
    gate.invalidate();

    // 此时即使拿着刚刚的 old_grant，也已经无法通过检查了！
    if (gate.accepts(*old_grant)) {
        return 2; // 异常: 已注销的授权绝不应被接受
    }

    // 4. 故障排除后，重新发起第二次使能申请:
    const auto next_grant = gate.arm(ec::CommandSource::host, true, true);

    // 5. 核心防御契约验证:
    //    - next_grant 必须合法且被接受
    //    - 极为关键：旧的 old_grant 必须依然被坚决拒绝（哪怕它们来自同一个来源）！
    if (next_grant && gate.accepts(*next_grant) && !gate.accepts(*old_grant)) {
        return 0; // 契约验证通过，完美防御旧指令死灰复燃！
    }

    return 3;
}
```

## 4. API 契约与生命周期

- **`arm(source, explicitly_authorized, locally_ready)`**：
  - 必须同时满足：来源合法（`remote`、`host` 或 `maintenance`）、显式授权为 `true`、本地就绪为 `true`。
  - **重要副作用**：每次调用 `arm()` 都会无条件先废除旧授权并推进代次！**切勿在每个控制循环（如 1ms 周期）内重复调用 `arm()`**，它只能在明确的“系统使能切换事件”发生时触发一次。
- **`accepts(grant)`**：
  - 纯状态核验函数，常数时间复杂度。要求门处于使能状态，并核验 `grant.source` 与 `grant.generation` 是否匹配；不检查目标是否过期。
- **`invalidate()`**：
  - 立即注销当前授权并推进代次。内部 64 位代次计数器耗尽后拒绝继续使能，不回绕复用。

**并发与重启约束**：授权门无内部锁，只由一个控制任务操作，不能从通信任务或 ISR 并发调用。MCU 重启时同时重置授权门、旧通道与会话；每个对象的本地代次不是跨对象或跨重启的全局身份。

## 5. 绝对红线：严禁从外部线协议反序列化 `Grant`

`Grant` 是单片机 MCU 本地内存生成的安全防线，**线上网络（如 CAN、串口、以太网）绝不允许直接传递 `Grant` 结构体**！
如果允许上位机直接通过串口把一个 `Grant` 塞给下位机，下位机的本地安全防护将彻底沦为摆设。
下位机应用层必须在本地完成所有的校验、解包和仲裁后，自行将本地颁发的 `Grant` 绑定到已接受的目标指令上。
