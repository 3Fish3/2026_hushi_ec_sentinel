# 授权速度控制链 (Velocity Loop)

源码: [velocity_loop.hpp](../../../include/ec/control/velocity_loop.hpp)、[velocity_loop.cpp](../../../src/control/velocity_loop.cpp)，位于 `ec::control` 命名空间。
对应契约测试: `tests/sil_tests.cpp` 中的 `velocity_contracts`，在主机环境的单任务组装范例见 [host_assembly.cpp](../../../examples/host_assembly.cpp)。

## 1. 为什么单纯的 PID 不能直接驱动真实电机？

很多同学在写电机控制时，会直接把传感器读数和目标转速喂给 PID，然后把 PID 的计算结果直接塞进 CAN 发送邮箱。
**在赛场上，这极易引发灾难性事故！**
单纯的 PID 只是一个数学运算器，它存在很多安全盲区：
- 它不知道上位机的目标指令是否由于网络卡顿已经超时了 500ms（陈旧指令依然在被执行）；
- 它不知道 CAN 总线上的电机反馈是不是早就掉线了（还在拿着 1 秒前的转速当成当前反馈做闭环）；
- 它不知道当前系统是否刚刚经历了一次急停重连（没有鉴别旧代次指令的能力）；
- 它不知道上层下达的目标转速是否超出了机械结构的物理极限。

**`VelocityLoop` 的使命：构筑带安全护栏的闭环执行链**
`VelocityLoop` 将 **PID 控制器**、**执行授权门 (Execution Gate)** 与 **严格的时效性 / 范围检查** 严密组合在一起：
只要发生任何异常（指令超时、反馈掉线、授权不匹配、转速超限、步长异常等），它会**立即主动注销当前授权、重置内部 PID 积分与历史状态，并拒绝产生控制输出（返回结果的 `output` 为 `std::nullopt`）**！

## 2. 输入输出规范与配置契约

- **统一的物理单位**：目标角速度与实测角速度必须是**严格对应同一根旋转轴的国际标准单位 `rad/s`**（严禁混用减速箱前后的转速）。
- **归一化的控制输出**：输出范围严格限制在 `[-1.0, 1.0]` 之间。它代表归一化的动力请求比例，**不是安培 (A)，也不是牛·米 (N·m)**。底层电调适配驱动负责将此归一化量映射为对应电机的协议控制电流。
- **量纲换算必须显式**：旧仓库的增益是 A/(rad/s)，本环的增益是"满量程分数/(rad/s)"。
  两者互换需要除以/乘以电流满量程(本板 C620 为 20 A)：`Kp_norm = Kp_A / 20`。
  直接把 `0.765855` 当归一化增益填进来会放大 20 倍；做旧参数回放对照时，输出要乘回满量程
  在 A 域比较，并且要连同旧的输出限幅(3000 raw ≈ 0.549316 A)一起保留，不能只比 Kp。
  `examples/host_app_example.cpp` 的相位 8 就是按这个口径做的(含不饱和与限幅两种数值断言)。
- **配置参数约束**：
  - `feedback_ttl`: 电机反馈数据的最大允许有效期（毫秒）。
  - `max_target_rad_s`: 非负有限值. 正值是可选的目标角速度绝对值上限, 超出时拒绝而不截断; **0明确表示不设软件速度上限**, 不是缺项或自动零目标. 反馈TTL、授权及协议电流边界照常生效.
  - `max_dt_s`: 允许的最大单步时间步长。超限后控制链撤销授权并拒绝本次输出，不等于物理机构已经停止。

**调用约束**：对象无内部锁，由一个控制任务拥有；`arm()`、`revoke()` 和 `step()` 不得并发调用。`ready` 必须来自本地自检。配置要求合法 TTL、非负有限的目标上限、正的最大dt, PID配置须有效、`limit_output=true`且输出范围不越出`[-1,1]`.以下数值是教学参数，不代表实车安全阈值；当前板级观察固件尚未接入此执行链。

## 3. 主机可运行示例

下面的代码演示了一个标准速度控制链的完整生命周期：授权申请、指令与反馈组装、单步安全计算与状态检查。

```cpp
#include "ec/control/velocity_loop.hpp"
#include <iostream>

// 主机可运行示例: 演示带安全授权护栏的速度闭环控制计算
int main() {
    // 1. 初始化速度环配置:
    //    参数结构: { PID配置, feedback_ttl(ms), max_target_rad_s(rad/s), max_dt_s(s) }
    const ec::control::VelocityLoopConfig config{
        // PID 参数: {kp=0.03, ki=0.25, kd=0, integral_limit=1.0, output_min=-1.0, output_max=1.0}
        {0.03f, 0.25f, 0.0f, 1.0f, -1.0f, 1.0f},
        ec::Lifetime{15}, // 反馈数据最长允许有效 15 ms
        80.0f,            // 目标最大转速绝对值不得超过 80.0 rad/s
        0.02f             // 拒绝超过 20 ms 的实际步长，不保证调度器以 50 Hz 运行
    };

    // 2. 构造速度闭环对象
    ec::control::VelocityLoop loop{config};

    // 3. 在系统使能事件触发时，向内部授权门申请代次授权令牌 (Grant)
    //    arm(控制来源, 显式使能标志, 本地自检通过标志)
    const auto grant = loop.arm(ec::CommandSource::host, true, true);
    if (!grant) {
        return 1; // 本地自检未通过或使能失败
    }

    // 4. 组装输入数据 (通常来自目标邮箱和反馈快照):
    //    - 目标指令: {目标值 20.0 rad/s, 本地接收时刻 received_at=100 ms, 指令有效TTL 40 ms, 绑定的代次令牌 *grant}
    const ec::Command<float> target{20.0f, ec::Tick{100}, ec::Lifetime{40}, *grant};
    //    - 反馈数据: {当前实测转速 0.0 rad/s, 采样时刻 100 ms, 状态 valid}
    const ec::Sample<float> feedback{0.0f, ec::Tick{100}, ec::Validity::valid};

    // 5. 在控制周期内执行闭环步进计算 step(当前时间戳, 周期步长 dt_s, 目标指令, 反馈样本)
    //    当前时间为 101 ms，步长为 0.001s (1 ms)
    const auto result = loop.step(ec::Tick{101}, 0.001f, target, feedback);

    // 6. 核心契约核验:
    //    - result.status: 必须为 VelocityStatus::active (正常激活计算状态)
    //    - result.output: 必须拥有合法的 float 输出值 (std::optional)
    if (result.status == ec::control::VelocityStatus::active && result.output) {
        // 取出归一化输出值进行后续的 CAN 编码与下发
        std::cout << "Control output calculated: " << *result.output << "\n";
        return 0; // 契约验证通过！
    }

    return 2;
}
```

## 4. 全状态枚举与故障熔断机制

`VelocityLoop::step` 会对当前输入进行极其严格的“漏斗式”前置检查，并返回具体的 `VelocityStatus` 状态码：

| 状态枚举值 | 产生该状态的具体原因 | 系统安全动作 |
|---|---|---|
| **`active`** | **全部条件通过！** 授权有效、时效新鲜、数值合法，成功输出 PID 控制量 | 正常产生控制输出（注：仍需底层 CAN 驱动确认成功送达） |
| **`invalid_config`** | 初始化的 `VelocityLoopConfig` 包含非法数值（如上限小于下限等） | **熔断撤销授权**，重置 PID，返回空输出 |
| **`no_command`** | 目标邮箱中没有任何指令（例如从未收到上位机数据） | **熔断撤销授权**，重置 PID，返回空输出 |
| **`stale_command`** | TTL 非法或目标不新鲜（到期瞬间即失效） | **熔断撤销授权**，重置 PID，返回空输出 |
| **`unauthorized`** | 门未使能，或指令携带的来源/代次不匹配（例如急停前残留的旧指令） | **熔断撤销授权**，重置 PID，返回空输出 |
| **`no_feedback`** | 未收到电机反馈或有效性不是 `valid` | **熔断撤销授权**，重置 PID，返回空输出 |
| **`stale_feedback`** | 电机反馈数据超时（流逝时间达到或超过配置的 `feedback_ttl`） | **熔断撤销授权**，重置 PID，返回空输出 |
| **`invalid_target`** | 目标转速为 NaN/Inf，或绝对值超过了 `max_target_rad_s` | **熔断撤销授权**，重置 PID，返回空输出 |
| **`invalid_dt`** | 步长 `dt_s` 非有限、非正、或超过了 `max_dt_s` | **熔断撤销授权**，重置 PID，返回空输出 |
| **`controller_error`** | PID 内部计算异常（如中间变量溢出等） | **熔断撤销授权**，重置 PID，返回空输出 |

> **关键容错特性**：
> 一旦上述任何一项错误发生，不仅本次调用返回空值，**内部的授权门也会被立即注销（`invalidate()`）**！这意味着系统进入了安全自锁状态。后续哪怕新指令送达，也必须经过上层状态机重新核准并显式调用 `arm()` 重新签发令牌，才能恢复运行！

---

若调用前已用 `CommandMailbox::read_fresh()` 过滤掉过期目标，`step()` 收到空值时会返回 `no_command`，而不是 `stale_command`。状态只描述本次计算，不替代机构安全状态机。

## 5. 新手常见误用警示

1. **每收到一帧上位机数据就调用一次 `arm()`**：
   - 严重错误！`arm()` 代表系统从禁用状态恢复到使能状态的“重握手”事件。如果每周期都调，系统代次会无限累加，不仅毫无安全防线，还会导致旧指令过滤机制彻底失效。
2. **把 `active` 状态直接等同于“电机已经转起来了”**：
   - `active` 仅代表下位机控制算法算出了输出。从算法输出到 CAN 报文发送、再到电调接收、最后驱动转子，中间还需要底层通信链路和电调物理硬件的配合。
3. **控制器熔断返回空输出时，简单粗暴地关闭所有驱动**：
   - 底盘也不能默认以零电流作为停止方案；对于重力轴，还需考虑支撑力矩丧失后的风险。保持、制动、失能或机械保护必须依据具体机构已确认的安全设计，本组件不替应用作此决策。
