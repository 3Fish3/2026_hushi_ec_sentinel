# 文档管理与撰写规范

目标是让新队员能逐步上手, 让开发者能查到可靠契约. 通俗不等于省略失败条件, 也不靠“绝对安全”“工业级”等表述代替证据.

## 1. 位置与职责

```text
README.md                  项目介绍、能力状态及入口
 docs/
 ├── README.md             学习路线和任务导航
 ├── 架构设计.md           全局决策与边界
 ├── 文档规范.md           文档维护约定
 ├── getting-started/      环境部署与首次运行
 ├── guides/               C++ 入门、代码导航、开发验证
 ├── modules/              核心、控制、传输、驱动说明
 ├── platforms/            主机与 STM32/HAL/RTOS 适配
 ├── boards/sentinel_f407/  板级资源、生成与构建
 └── robots/sentinel/      实施与验收、现有能力与待确认 Checklist
```

完整模块说明集中在 `docs/modules/`, 不在 `include/`、`src/` 各放一份副本. 头文件注释仍保留单位、输入条件、返回值和并发约束. 独立工具确需就地操作入口时可放简短 README, 链接主要说明而非重复整篇教程.

## 2. 内容只保留一个主要维护位置

- 全局决策见架构设计; 教学解释链接它, 不另定一套规范.
- 环境安装见环境部署; 板级配置/生成/构建命令见板级文档; 实机操作与验收记录见机器人文档.
- 模块说明讲通用接口, 机构映射和未决参数留在机器人 Checklist.
- README 保持简短导航, 不重新收录所有模块契约和构建步骤.
- 迁移文件时更新相对链接, 不长期保留内容相同的新旧两份正文.

示例可以包含解释所必需的测试数值, 但须标为演示值, 不是把它升级成新的实车参数来源. 版本锁定和真实接口以仓库配置/源码为准, 文档变更时同步核对.

## 3. 模块文档的内容检查项

按先易后难组织, 小组件可合并章节, 不为凑章数写空话:

1. 解决什么问题, 给一个具体场景.
2. 不负责什么, 防止越界使用.
3. 核心概念、API 或组件选择.
4. 最小示例, 明确是可运行程序、可编译函数片段还是伪代码.
5. 输入输出的单位、合法范围和有效性.
6. 初始化、失败、撤销与恢复行为.
7. 所有权、线程/ISR 条件、内存与时序限制.
8. 源码、测试、相关文档链接与常见错误.

“可运行”示例应有必要头文件和 `main`, 不能暗藏 `stop_motor_safely()` 等未定义函数. 与实际硬件交互的示意片段需显式写出前提, 不让省略的临界区看起来像可直接部署的实现.

## 4. 事实与表达

- 明确区分已实现、离线验证、实机验证及待决策项.
- 不将模拟器参数或测试输出当作硬件性能证明; 不作固定编译耗时、任意平台兼容或零故障保证.
- “无输出”不等于“已经停止”, `accepted` 不等于“设备已执行”.
- 注释使用简体中文, 技术符号保持原文. 新术语先作简单解释, 再展开限制.
- 避免“炸车”“根绝所有问题”等夸张表述; 直接说明触发条件、后果和正确做法.
- 示例路径可用通用安装目录并注明替换, 不依赖个人真实盘符或用户名. 未知仓库 URL 使用明确占位符, 不编造地址.

## 5. Markdown 与可选 Obsidian

文档本体为 Git 管理的 Markdown. 可用 Obsidian 打开仓库根目录作为 Vault; 个人 `.obsidian/` 配置不提交, 不要求读者安装 Obsidian.

- 使用标准相对链接, 不用 `[[双链]]` 作为唯一引用方式.
- `docs/` 文档采用 YAML Frontmatter: `date` 为创建日期, `updated` 为最近实质修改日期, `tags` 为小写标签. 根 README 不强制添加元数据.
- 图可用 Mermaid, 关键结论必须同时有文字, 不依赖某个渲染器才能理解.
- 需要图片附件时放 `docs/assets/`, 按主题分目录; 不为未使用资源预建空目录.
- 避免依赖 Markdown 行尾双空格换行, 可用段落或列表, 便于空白检查.

## 6. 验证方式

修改文档后检查本地链接及标题锚点、API 与源码一致性, 对可运行示例做适当编译验证. 环境/命令变更尽量在新的构建目录检查, 避免现有 CMake 缓存掩盖遗漏参数.

不能为验证文档而擅自运行 CubeMX 覆盖、烧录或运动命令; 这些步骤可先作静态核对并明确未执行. 文档检查不默认要求为每篇新增专用测试框架或重复全套固件测试.
