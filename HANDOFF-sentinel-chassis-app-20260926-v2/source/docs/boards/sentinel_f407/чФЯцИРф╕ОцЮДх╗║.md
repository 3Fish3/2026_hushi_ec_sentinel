# Sentinel 板级生成与构建 (Board Build & Generation)

这是当前哨兵主控板（RoboMaster C 板）固件离线交叉编译、二进制静态安全审计与 STM32CubeMX 再生成的官方核心操作手册。
只要你已按 [环境部署](../../getting-started/环境部署.md) 装好了第二阶段的 ARM 工具链和官方 SDK，即可在电脑上直接编译出固件；**编译仓库现有代码完全无需安装或运行 STM32CubeMX**！(^_^)v

只需快速切换已有角色或刷写时, 可使用[固件刷写工具与上位机对应表](../../guides/固件刷写与上位机对应.md); 本文保留命令行构建与底层说明。

所有命令均在 **PowerShell 7 终端、仓库根目录**下执行。请先确认路径变量指向你电脑上的实际工具包目录。

---

## 1. 编译非运动观察固件并执行静态符号审计

依次执行以下命令，先生成完整板级固件，再显式运行 Python 离线检查；仅执行 `cmake --build` 不会自动运行该检查：

```powershell
# 遇到未捕获的错误立即停止脚本执行
$ErrorActionPreference = 'Stop'

# 1. 设置工具链与官方 SDK 路径变量 (请替换为你电脑上的实际解压绝对路径)
$arm = 'C:/Tools/arm-gnu-toolchain-14.2.rel1'                       # Arm GNU 工具链根目录 (不带末尾 bin)
$sdk = "$env:USERPROFILE/STM32Cube/Repository/STM32Cube_FW_F4_V1.28.3" # 完整 STM32CubeF4 1.28.3 SDK 路径

# 2. 调用 CMake 配置交叉编译工程
#    -S .                           : 指定当前仓库根目录
#    -B build/s1-debug              : 输出产物隔离在 build/s1-debug 独立目录中
#    -G Ninja                       : 使用高性能 Ninja 构建工具
#    -DCMAKE_BUILD_TYPE=Debug       : 生成包含完整 DWARF 调试符号的 Debug 固件
#    -DCMAKE_TOOLCHAIN_FILE=...     : 引入针对 arm-none-eabi 的交叉编译工具链定义
#    -DARM_GNU_ROOT=...             : 显式传入交叉编译器根目录
#    -DEC_BUILD_SENTINEL_S1=ON      : 核心开关：启用 Sentinel S1 板级完整固件构建
#    -DEC_STM32CUBE_F4_ROOT=...     : 传入官方底层 SDK 路径 (会自动核验 package.xml 的 SHA256)
#    -DEC_FIRMWARE_ID=s1-development: 注入固件诊断字符串标签，不替代 Git 状态与产物哈希
cmake -S . -B build/s1-debug -G Ninja `
  -DCMAKE_BUILD_TYPE=Debug `
  "-DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake" `
  "-DARM_GNU_ROOT=$arm" `
  -DEC_BUILD_SENTINEL_S1=ON -DEC_S5_GM6020_BENCH=OFF `
  "-DEC_STM32CUBE_F4_ROOT=$sdk" `
  -DEC_FIRMWARE_ID=s1-development
if ($LASTEXITCODE -ne 0) { throw 'CMake 交叉编译配置生成失败，请核对 SDK 路径与哈希' }

# 3. 编译生成 ELF、BIN、HEX 固件与内存映射 MAP 文件
cmake --build build/s1-debug
if ($LASTEXITCODE -ne 0) { throw '固件交叉编译链接失败，请检查编译错误提示' }

# 4. 运行离线安全审计脚本: 检查 ELF 文件符号表与硬件配置
#    --elf: 刚刚编译生成的 ELF 固件绝对/相对路径
#    --nm : 工具链中的 arm-none-eabi-nm 符号提取程序路径
python boards/sentinel_f407/check_firmware.py `
  --elf build/s1-debug/boards/sentinel_f407/sentinel_s1.elf `
  --nm "$arm/bin/arm-none-eabi-nm.exe"
if ($LASTEXITCODE -ne 0) { throw '固件静态安全审计未通过，严禁下载烧录！' }
```

构建会同时产出一个**非部署**验证产物 `ec_link_verify` (同一工具链与链接脚本, 但只引用通用组件、
不实现 APP 钩子), 链接后由 `boards/sentinel_f407/check_link_verify.py` 核对 17 组符号是否真的
被链接进 ELF —— 板级目标启用 `--gc-sections`, 源码编进静态库并不等于被链接。它不是可烧录镜像,
默认固件 `sentinel_s1` 的无输出审计规则也不因它放宽。板级 CMake 需要 Python3 解释器(配置阶段强制).

默认 `EC_S1_UART6_MONITOR=ON`, 启用 USART6 只读观测服务; 可在同一构建配置中设置 `-DEC_S1_UART6_MONITOR=OFF` 关闭该服务, 不会新增电机控制能力. 面板与协议使用见 [串口观测与应用接入](../../guides/串口观测与应用接入.md).

编译与审计成功后，固件文件将位于 `build/s1-debug/boards/sentinel_f407/` 目录下：
- **`sentinel_s1.elf`**：包含完整调试符号的可执行二进制，用于 OpenOCD / GDB 调试；
- **`sentinel_s1.hex` / `.bin`**：用于 ST-Link 烧录的裸机镜像；
- **`sentinel_s1.map`**：详细的芯片 Flash 与 SRAM 内存段分配映射表。

> **编译 Release 版本优化固件**：
> 将命令中的构建目录改为 `build/s1-release`，配置改为 `-DCMAKE_BUILD_TYPE=Release`，重新执行上述完整命令即可。切勿在同一个目录中混用 Debug 与 Release 缓存！

### 1.1 S5 GM6020 单电机镜像

使用前文已设置的 `$arm`、`$sdk`, 为 S5/v6 另建目录, 不覆盖旧实物构建/备份或 S1–S4 缓存. 示例 ID4 来自最近采集记录, **实际 ID 仍须先被动核对**; 修改 `EC_S5_GM6020_ID` (1..7) 会同时更新设备、组与槽, 不修改电机保存值:

```powershell
cmake -S . -B build/bench-s5v6-arm-Release -G Ninja `
  -DCMAKE_BUILD_TYPE=Release `
  "-DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake" `
  "-DARM_GNU_ROOT=$arm" `
  -DEC_BUILD_SENTINEL_S1=ON -DEC_S5_GM6020_BENCH=ON -DEC_S1_UART6_MONITOR=ON `
  -DEC_S5_GM6020_ID=4 `
  "-DEC_STM32CUBE_F4_ROOT=$sdk" -DEC_FIRMWARE_ID=s5-v6-id4-release
if ($LASTEXITCODE -ne 0) { throw 'S5 配置失败' }
cmake --build build/bench-s5v6-arm-Release --target sentinel_s1
if ($LASTEXITCODE -ne 0) { throw 'S5 构建失败' }
python boards/sentinel_f407/check_firmware.py `
  --elf build/bench-s5v6-arm-Release/boards/sentinel_f407/sentinel_s1.elf `
  --nm "$arm/bin/arm-none-eabi-nm.exe" --allow-gm6020-bench
if ($LASTEXITCODE -ne 0) { throw 'S5 镜像检查失败' }
```

`image_role` 必须为 `S5 ACTUATING GM6020 bench`. 不带该显式检查选项时, S5 标记应被非运动检查拒绝. **同名 `sentinel_s1.elf` 在此目录中是可驱动电机的镜像**, 不能拿 `result=pass` 冒充非运动保证. 启动默认不使能, 但固件会发送零电流帧. 操作说明见 [GM6020 单电机测试](../../guides/GM6020单电机测试.md).

### 1.2 整车无主动驱动采集镜像

`EC_BUILD_SENTINEL_CAPTURE=ON` 增加独立目标 `sentinel_capture`, 与 S5 选项互斥. DJI 仅接收, DM 仅发送固定白名单参数/状态读取, 不驱动、不写设置; 它不是严格零 CAN TX 的 S1 镜像. 构建自动执行专用 `check_capture.py`, 默认 S1 审计规则不变. 构建命令、Python 面板与人工编码器记录见 [哨兵只读采集与人工标定](../../guides/哨兵只读采集与人工标定.md).

### 1.3 正式 APP 镜像 (九 DJI + 一 DM)

`EC_BUILD_SENTINEL_APP=ON` 增加独立目标 `sentinel_app`, 与 S1/S5/采集选项互斥 (三个角色必须各用独立构建目录, CMake 配置阶段就会拒绝混用). 它是**会驱动执行器的镜像**: 1 kHz 控制任务、九 DJI + 一 DM 的配置/仲裁/感知/执行路径、USART1 业务协议与 100 Hz 观测发布全部链接进镜像; 与 S1/S5 不同, 它的审计规则是“APP 路径确实被链接进来”, 而不是“镜像里没有发送路径”.

```powershell
cmake -S . -B build/app-arm-Debug -G Ninja `
  -DCMAKE_BUILD_TYPE=Debug `
  "-DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake" `
  "-DARM_GNU_ROOT=$arm" `
  -DEC_BUILD_SENTINEL_APP=ON `
  "-DEC_STM32CUBE_F4_ROOT=$sdk" -DEC_FIRMWARE_ID=development
if ($LASTEXITCODE -ne 0) { throw 'APP 配置失败' }
cmake --build build/app-arm-Debug
if ($LASTEXITCODE -ne 0) { throw 'APP 构建失败' }
```

构建后自动执行 `boards/sentinel_f407/check_sentinel_app.py` (可用 `--elf`/`--nm` 手动重跑). 它核对的是离线事实, **不代替任何实机验证**:

- 镜像身份: `g_ec_s1_build_id` 必须以 `app-` 开头, 硬浮点 ABI, 无未解析符号, 无 `malloc`/C++ 分配依赖, 无未使用的 nosys I/O 桩;
- APP 路径存在性: `ec_app_init`/`ec_app_control_tick`/`ec_app_control_task_entry`/`ec_app_route`/`ec_app_link_bytes`/`ec_registry_publish_app` 与 `encode_dji`/`DjiTxGroup`/`HAL_CAN_AddTxMessage` 必须全部被链接; `ec_board_app_control`/`ec_board_app_commit` 必须是**强定义** (弱定义说明镜像还在用“不下发任何输出”的默认钩子);
- 控制任务静态存储 `appControlStack`/`appControlTaskBuffer` 必须在镜像里 (静态栈, 不占 FreeRTOS heap);
- 部署配置摘要 `ec_app_deployment_summary` 必须可从**未压缩镜像**读出, 且声明为 `real_deployment`、合成值 0、已装配槽 0 (当前没有实测参数)、容量 9 DJI + 1 DM、已验接线 9 + 1.

产物在 `build/app-arm-Debug/boards/sentinel_f407/` 下: `sentinel_app.elf` / `.hex` / `.bin` / `.map`. **同名 `.elf` 在不同目录里是不同角色**: 拿 S1 目录的 `result=pass` 冒充 APP 镜像检查结论是不成立的. 上板、供电、烧录与实机动作仍需单独授权; 本文与审计脚本都不授权烧录.

部署配置表在 `boards/sentinel_f407/include/board_app_config.hpp`: 目前只有**已验证接线**(CAN1 两颗 GM6020 反馈 `0x208`/`0x20a`, CAN2 六颗 C620 `0x201`–`0x206` 与 ID7 的 C610 `0x207`, 达妙在 CAN1)与软件时序策略, **没有**机构分配、传动比、方向、电流上限、关节零位/范围与 DM 量程 —— 因此镜像启动后如实报告“配置不齐备”, 不给任何域执行资格. 待确认清单与回填规则见 [正式APP接入说明](../../robots/sentinel/正式APP接入说明.md).

### 1.4 正式APP单GM6020 ID4台架配置

仅用于已授权、具备物理硬切的固定单电机台架. 在独立构建目录启用 `EC_BUILD_SENTINEL_APP=ON` 与 `EC_APP_GM6020_BENCH=ON`, 复用正式APP执行/协议路径; 不是S5固件, 也不是合成夹具. 只装配CAN1 ID4到main_yaw域, 其它执行器不装配. 整车默认选项仍为OFF, 保留零装配槽与真实遥控首启要求. 台架显式采用maintenance-only首启, 不伪造遥控帧, 不授权本地或Jetson正常来源.

```powershell
cmake -S . -B build/app-gm6020-manual-arm-Release -G Ninja `
  "-DCMAKE_BUILD_TYPE=Release" "-DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake" `
  "-DARM_GNU_ROOT=$arm" "-DEC_STM32CUBE_F4_ROOT=$sdk" `
  -DEC_BUILD_SENTINEL_APP=ON -DEC_APP_GM6020_BENCH=ON `
  -DEC_S1_UART6_MONITOR=ON -DEC_FIRMWARE_ID=20260926-manual
if ($LASTEXITCODE -ne 0) { throw 'APP单电机台架配置失败' }
cmake --build build/app-gm6020-manual-arm-Release --target sentinel_app
if ($LASTEXITCODE -ne 0) { throw 'APP单电机台架构建失败' }
```

镜像标识为 `app-gm6020-id4-<label>`, 构建自动给审计脚本传 `--gm6020-bench`; 手动审计也须明确指定, 不会被默认零装配整车审计接受. 配置定义在 `boards/sentinel_f407/include/board_app_bench_config.hpp`, 参数与操作口径见 [正式APP接入说明](../../robots/sentinel/正式APP接入说明.md) §5.2. `20260926-manual` Release BIN为195,112 B、链接RAM为102,392 B, 主RAM余28,680 B; 未加入S5的64 KiB波形缓冲. 自由台架采用显式人工参考和连续角度, 不再设0/2π伪机械限位; 上电不自动置零, 整车有界配置不变.

### 1.5 正式APP四电机CAN1台架

与单GM6020选项互斥, 不改变整车默认零装配配置. 全部CAN1: GM6020 ID4、**M3508 ID2、M2006 ID3**、J4310控制ID1/反馈ID0; M2006不用ID7, 避免0x1FF组被GM6020识别为电压命令; M3508不用ID1, 避免反馈0x201低8位命中达妙控制ID1. 只用于自由裸电机的人工预验, 不可直接部署到整车机构.

```powershell

  "-DCMAKE_BUILD_TYPE=Release" "-DCMAKE_TOOLCHAIN_FILE=cmake/arm-none-eabi.cmake" `
  "-DARM_GNU_ROOT=$arm" "-DEC_STM32CUBE_F4_ROOT=$sdk" `
  -DEC_BUILD_SENTINEL_APP=ON -DEC_APP_FOUR_MOTOR_BENCH=ON -DEC_APP_GM6020_BENCH=OFF `
  -DEC_S1_UART6_MONITOR=ON -DEC_FIRMWARE_ID=20260926-id3
```

产物位于`build/app-four-motor-arm-Release/boards/sentinel_f407/`, 标识`app-four-motor-20260926-id3`. 自动审计明确使用`--four-motor-bench`, 必须为3 DJI + 1 DM; 默认整车及单GM审计均拒绝此镜像. 本次Release BIN196,152 B、链接RAM102,392 B, 未加S5波形缓存. 上位机用`--mechanism bench`, 人工流程及参考参数说明见[正式APP接入说明](../../robots/sentinel/正式APP接入说明.md) §5.3. 构建通过不授权烧录或动作测试.

### 1.6 实车底盘调试APP

独立目录`build/app-chassis-arm-Release`, 使用`EC_BUILD_SENTINEL_APP=ON`和`EC_APP_CHASSIS_COMMISSIONING=ON`, 与两种bench选项互斥. 构建目标`sentinel_app`, 镜像前缀`app-chassis-`, 审计显式添加`--chassis-commissioning`. 快速刷写工具已有对应角色, 会传递完整构建参数.

## 2. 离线安全检查脚本 (`check_firmware.py`) 究竟在检查什么？

很多同学可能会好奇：“既然代码都编译通过了，为什么还要多此一举跑一个 Python 检查脚本呢？”
这是为了在**离线阶段增加一组明确、可重复的产物检查**，提前发现已覆盖的配置和链接错误。
`check_firmware.py` 会使用 `nm` 工具深度剖析刚刚链接完成的 ELF 目标文件，逐一核实以下高危项：
1. **防误动符号审计（至关重要）**：
   在当前的“非运动观察固件”阶段，脚本扫描符号表，检查指定的 PWM 初始化/启动、`MX_USB_`、`encode_dji` 与 `HalCanTx` 符号。命中会报错，但这不是所有硬件输出路径的证明，例如直接调用 `HAL_CAN_AddTxMessage` 不在当前禁止符号表中。
2. **底层硬件向量与符号完整性**：
   核验 Cortex-M4 硬件浮点指令集（Hard-Float）、系统初始堆栈指针（MSP）、向量表重定向与必要的中断服务函数（如串口空闲中断、DMA 中断）符号是否健全存在。
3. **硬件时钟与分频静态核对**：
   解析 `.ioc` 配置文件与生成的 `spi.c` 代码，核实 SPI1 时钟分频是否严格保持在 5.25 MHz（避免超出 BMI088 的 10 MHz 通信频率规格；超频不等同于必然损坏器件）。
4. **Flash 容量越界检查**：
   确保编译出的 `.bin` 文件绝对没有超出 STM32F407IGH6 芯片的 1 MB Flash 容量上限。

此外还检查必要诊断/保护符号、未解析符号与指定的分配/nosys I/O 依赖。Debug 中 `optional` 可能保留 placement new (`_ZnwjPv`), 它只返回传入地址, 不分配内存; 检查器仅豁免这个明确符号, 不豁免普通 new/new[] 或 malloc。输出的 ELF/BIN SHA256 用于记录产物身份，不是与预置可信固件哈希比对。脚本未完整验证 NVIC 优先级、RAM/栈余量、全部生成代码或实际外设时序；这些仍需代码检查及实机验收。

> ⚠️ **认知警示**：
> 静态审计输出 `result=pass` 仅代表代码满足了上述离线安全契约，**绝不自动代表获得了上车烧录和通流动力的许可**！实机测试必须遵循 [哨兵实施与验收](../../robots/sentinel/实施与验收.md)。

## 3. 什么时候需要重新生成 CubeMX 工程？如何操作？

**再次强调**：平时修改控制算法、协议编解码或增加诊断代码，**绝对不需要碰 STM32CubeMX**！
只有当你需要：
1. 为 C 板分配新的硬件引脚（例如新增一个按键中断或 LED 状态灯）；
2. 调整系统时钟树分频；
3. 修改串口或 SPI 的 DMA 数据流通道配置；
此时才需要使用 STM32CubeMX 重新生成工程。

### 重新生成的安全规范步骤：

1. **先做 Git 暂存与差异比对**：
   确保当前工作区没有未提交的杂乱修改，防止生成器覆盖有用代码。
2. **（可选）应用项目基线补丁 `patch_ioc.py`**：
   `patch_ioc.py` 将本项目选定的引脚、晶振分频与 DMA 配置写入 `.ioc`，不是自动保留用户定制配置的修复器；`regenerate.ps1` 不会调用它。确认有意重置这些配置时才执行：
   ```powershell
   python boards/sentinel_f407/patch_ioc.py
   if ($LASTEXITCODE -ne 0) { throw 'IOC 基线补丁应用失败' }
   git diff -- boards/sentinel_f407/cubemx/sentinel_s1/sentinel_s1.ioc
   ```
3. **唤起 CubeMX 自动化生成脚本**：
   使用已安装的 STM32CubeMX 6.18.1 执行无头生成：
   ```powershell
   # 传入 CubeMX 实际安装路径执行静默重新生成
   ```

## 4. 烧录与校验 (已验证的 ST-Link V2 / OpenOCD 路线)

构建不会自动烧录. 在已获授权的目标上, 先停止电机输出并使执行器处于无动力状态, 关闭占用串口或 SWD 的其他工具; 保持主控供电. 若电池疑似休眠或连接掉线, 暂停核对, 不循环重试. 以下步骤不改 Option Bytes、不解除读保护、不全片擦除, 只编程新镜像覆盖的扇区. 按用户2026-09-25确认的项目规则, 已授权烧录不再额外预读保存Flash备份; 镜像由仓库源码重建, 仍保留目标识别和写后校验, 既有备份不删除.

**终端 A** (仓库根目录, PowerShell 7): 核对只有一个 ST-Link V2, 启动调试服务. 路径按实际安装位置修改; 本机探针不能用 Windows 显示的序列号直接匹配 OpenOCD.

```powershell
$ErrorActionPreference = 'Stop'
$probes = @(Get-PnpDevice -PresentOnly | Where-Object {
  $_.InstanceId -like 'USB\VID_0483&PID_3748\*'
})
if ($probes.Count -ne 1) { throw '必须仅连接一个已确认目标的 ST-Link V2' }
$ocd = 'C:/Tools/OpenOCD'
& "$ocd/bin/openocd.exe" -s "$ocd/openocd/scripts" `
  -f interface/stlink.cfg -c 'transport select dapdirect_swd' `
  -f target/stm32f4x.cfg -c 'bindto 127.0.0.1' -c 'adapter speed 950' `
  -c 'tcl port disabled' -c 'telnet port disabled'
```

看到芯片连接成功及 `Listening on port 3333` 后, 在**终端 B** (同样位于仓库根目录) 执行. 使用 S1 镜像时将 `$image` 改为对应已检查的 ELF, 不混用其他构建目录.

```powershell
$ErrorActionPreference = 'Stop'
$arm = 'C:/Tools/arm-gnu-toolchain-14.2.rel1'
$image = 'build/s5-gm6020/boards/sentinel_f407/sentinel_s1.elf'
if (-not (Test-Path -LiteralPath $image)) { throw '镜像不存在' }
$out = 'build/flash-' + (Get-Date -Format 'yyyyMMdd-HHmmss-fff')
if (Test-Path -LiteralPath $out) { throw '烧录日志目录已存在, 不覆盖' }
New-Item -ItemType Directory -Path $out | Out-Null
@"
set pagination off
set remotetimeout 90
target extended-remote 127.0.0.1:3333
monitor halt
if (*(unsigned int*)0xe0042000 & 0xfff) != 0x413 || *(unsigned short*)0x1fff7a22 != 1024
  monitor resume
  quit 3
end
monitor program {$image} verify reset
disconnect
"@ | Set-Content -LiteralPath "$out/program.gdb" -Encoding utf8
& "$arm/bin/arm-none-eabi-gdb.exe" --batch -q $image -x "$out/program.gdb" 2>&1 |
  Tee-Object -FilePath "$out/program.log"
if ($LASTEXITCODE -ne 0) { throw '烧录命令失败, 先检查编程/校验/复位各阶段日志, 不盲目重刷' }
Get-FileHash -LiteralPath $image -Algorithm SHA256
```

应看到 `Verified OK` 与复位日志. 在终端 A 用 Ctrl+C 结束 OpenOCD, 然后打开对应 Python 面板核对固件/协议及反馈, **不自动开始运动**. GDB 脚本只对当前 STM32F405/407 系列 ID 和 1 MiB Flash 生效; 目标不符时停止, 不删检查来强行烧录. `build/flash-*/` 不入 Git, 保存源码构建镜像身份和烧录日志; 历史已有Flash备份仍须保留. `program ... verify reset`已让目标运行, 不再追加冗余`monitor resume`. 此处命令不意味着任意探针、驱动及路径组合均已验证.

## 5. 常见编译问题排错速查

- **CMake 提示 `Unexpected CubeF4 package metadata`**：
  - 原因：指定的 `EC_STM32CUBE_F4_ROOT` 路径不是纯正完整的 1.28.3 官方包，或者其中的 `package.xml` 发生过修改。
  - 解决：重新下载或更新至官方完整的 1.28.3 SDK，切不可私自修改 `sdk.cmake` 中的哈希值。
- **链接时出现 nosys `_read/_write` 等“未实现”警告**：
  - 当前观察固件通过 `--gc-sections` 裁掉未用依赖，检查脚本会核对指定符号未留在最终产物中；未来实际使用 libc I/O 时需实现相应接口，不能照搬此结论。真正的 `undefined reference` 是链接错误，必须定位缺失依赖，不能作为已知警告忽略。
- **固件检查脚本报 `Unexpected actuator/USB symbol` 或 `S2-S4 image must not link motor command encoding or CAN TX adapter`**：
  - 说明你在非运动固件的代码路径中，不小心调用了电机控制编码、PWM 或 CAN 发送相关的函数。请检查代码调用链并切断物理发送依赖。
