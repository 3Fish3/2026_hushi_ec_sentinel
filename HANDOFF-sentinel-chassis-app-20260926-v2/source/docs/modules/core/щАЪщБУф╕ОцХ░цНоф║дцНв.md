# 通道与数据交换 (Channels)

源码: [channel.hpp](../../../include/ec/channel.hpp)，类型位于 `ec` 命名空间。对应契约测试: `tests/core_tests.cpp` 中的 `gate_and_channels`。

## 1. 为什么我们需要通道机制？

在嵌入式开发中，多个 FreeRTOS 任务或中断服务函数（ISR）经常需要共享数据（例如：“上位机下发的最新速度目标”、“电机最新的反馈角度”、“发弹微动开关触发事件”）。
很多同学第一反应是：“直接定义一个全局变量，谁用谁读不就行了吗？如果怕编译器优化，大不了加个 `volatile` 关键字呗？”

**这是嵌入式并发中极大的认知误区！**
- **原子性缺失**：在 32 位 MCU 上，即使单个 32 位整型的读写是单条汇编指令，但我们的数据通常由**“数值 + 采样时间戳 + 数据有效性标记”**共同构成。如果一个任务正在写这 3 个字段，刚写完第 1 个字段就被更高优先级的控制任务打断并读取，控制任务就会读到拼凑的“半新半旧”脏数据！
- **`volatile` 不等于线程同步**：`volatile` 要求编译器按其访问语义处理读写，但它**完全不提供内存屏障、不提供互斥锁、更无法保证多字段操作的原子性**。

因此，核心层设计了 4 种语义明确、有界内存的数据通道：

| 数据类型 | 采用的通道组件 | 核心行为与设计初衷 |
|---|---|---|
| **连续控制目标** | `CommandMailbox<T, Lock>` | **最新值覆盖旧值**：机器人只关心“当前这一瞬间”的目标速度，哪怕之前卡顿丢了中间目标也不排队补发，`read_fresh()` 会在取出时自动滤除过期目标。 |
| **状态 / 传感器反馈** | `Snapshot<T, Lock>` | **一致性快照**：在临界区保护下一次性原子拷贝 `Sample<T>` 的“数值 + 采样时刻 + 有效性”，杜绝脏数据。 |
| **离散动作触发** | `EventQueue<T, N, Lock>` | **有界先进先出队列 (FIFO)**：用于“发射一颗弹丸”、“自检通过”等单次事件。队列满时明确拒绝新事件并返回 `full`，绝不静默丢失。 |
| **无时间元数据的简单值** | `LatestValue<T, Lock>` | 受锁保护的最新单一数值安全复制。 |

## 2. 通道组件不负责什么（安全边界）

为了保持职责纯粹，通道容器仅负责**底层并发内存拷贝的安全一致性**：
- 它**不负责身份鉴权**：邮箱里存放的数据新鲜，并不代表发指令的上位机已经获得了当前代次的控制授权（必须配合 [授权门](授权门.md) 核验）。
- 它**不负责传感器物理校准**：`Snapshot` 在所有读写遵守同一有效锁策略时提供一致副本，但不能证明这颗传感器出厂标定是准确的。
- 离散事件队列必须在应用层显式核对有效性，切不可盲目执行出队的旧指令。

## 3. 主机可运行示例

下面的示例演示如何使用 `Snapshot` 在临界区保护下安全地发布和读取带有时间戳的电机反馈：

```cpp
#include "ec/channel.hpp"
#include "ec/platform/host.hpp"
#include <iostream>

// 主机可运行示例: 演示 Snapshot 状态快照的发布、读取与时效验证
int main() {
    // 1. 声明临界区锁策略对象 (主机环境使用基于 std::mutex 的互斥锁)
    ec::host::MutexCriticalSection lock;

    // 2. 构造快照通道对象，注入临界区锁的引用
    //    该对象内部持有数据结构及锁引用，容量和内存严格在栈上确定
    ec::Snapshot<float, ec::host::MutexCriticalSection> feedback{lock};

    // 3. 发布者 (通常是 CAN 接收中断或传感器采集任务):
    //    原子发布一份最新的样本数据:
    //    参数结构体字段: { 数值 (2.0 rad/s), 采样时间戳 (100 ms), 有效性标记 (valid) }
    feedback.publish({2.0f, ec::Tick{100}, ec::Validity::valid});

    // 4. 消费者 (通常是 1 kHz 的运动控制闭环任务):
    //    原子读取当前快照中保存的最新样本拷贝
    const auto sample = feedback.read();

    // 5. 校验读取结果:
    //    - sample: 是否成功读到了数据 (返回 std::optional)
    //    - sample->fresh_at(当前时刻, 允许的有效生命期 TTL):
    //      在当前时间 105 ms 下，若 TTL 为 10 ms，则 (105 - 100 = 5 ms) < 10 ms，判定数据依然新鲜！
    //    - sample->value: 取出实际数值 2.0 rad/s
    if (sample && sample->fresh_at(ec::Tick{105}, ec::Lifetime{10}) && sample->value == 2.0f) {
        return 0; // 契约验证通过
    }

    return 1; // 验证失败
}
```

> **生命周期核心纪律**：
> 在上述示例中，`lock` 和 `feedback` 均分配在 `main` 函数的作用域内。在实际固件中，锁与通道通常作为系统级全局组件或静态组件组装。**极其危险的低级错误是将局部栈对象的引用传递给长期运行的 FreeRTOS 任务或 ISR**！

## 4. 内存容量与对象生命周期契约

- **受约束类型**：进入通道的元素类型 `T` 必须满足 C++20 `ChannelValue` 约束（可平凡复制、无异常默认/拷贝构造与拷贝赋值，总大小 $\le 256$ 字节）。`std::string` 或带虚函数的非平凡类型不满足约束；裸指针成员却可能通过，不能靠 concept 保证其生命周期或被指向对象的并发安全。实际存储的 `Command<T>`、`Sample<T>` 等完整包裹类型也须满足通道大小限制。
- **静态有界容量**：`EventQueue<T, N>` 中的容量 `N` 在编译期模板参数中写死，运行期绝不进行动态扩容。
- **引用生命周期**：被引用的锁对象必须先于通道构造，且在通道析构之后才能销毁。在启动并发多任务前必须完成所有通道的初始化构造。

## 5. 常见并发误用排错

1. **从邮箱中读出指令后未经授权直接下发**：
   - 错误：`auto cmd = mailbox.read_fresh(); if (cmd) send_to_motor(*cmd);`
   - 正确：必须核对 `cmd->grant` 是否匹配当前控制器的合法代次授权（见 [授权门](授权门.md)）。
2. **在持有非递归锁的情况下嵌套调用通道**：
   - 如果同一个任务在同一个临界区内先后访问两个共用同一把非递归锁的通道，会导致自死锁！临界区内的代码必须极简、快速且独立。
3. **把未知或错误的数据标记为 `valid`**：
   - 传感器未完成标定或解析校验失败时，必须标记为 `Validity::invalid`，切不可只为了有数据输出而强行伪造 `valid` 状态。
