# 开发与验证流程

在机器人电控开发中，“在电脑上写完代码直接烧进车里看效果”是极其危险且低效的习惯。哪怕只是一个正负号写反、或者单位没有换算，都可能导致电机瞬间全功率暴冲飞车，造成硬件损毁甚至人身伤害！

为了彻底杜绝此类隐患，本项目严格推行 **“分级递进验证流程”**：先在主机上通过确定性的离线单元测试和软件在环（SIL）仿真发现并修复覆盖范围内的逻辑缺陷；只有在离线证据充分、且获得专人安全授权的前提下，才允许进入真实硬件的单步观察与受控动作。

---

## 1. 动手改动代码前：明确需求与契约

在敲击键盘修改任何代码前，请先花 5 分钟完成以下核对：
1. **明确改动归属的层级**：
   - 属于核心算法？平台适配？还是板级配置？请参考 [项目分层与代码导航](项目分层与代码导航.md)，切勿越界破坏分层依赖（例如把 FreeRTOS 任务代码塞进通用核心库）。
2. **确认当前 Git 工作区干净**：
   - 使用 `git status` 确认没有他人未提交的改动或冲突，避免无意中覆盖或混入无关修改。
3. **查阅受影响组件的接口契约**：
   - 核对函数的入参单位（是否为标准 SI 单位 rad/s、rad、m/s？）、时间有效性要求（TTL 毫秒数）、对象所有权（是引用传递还是值拷贝？）。切忌凭函数名“想当然”地猜测接口行为。
4. **涉及实车参数时的规则**：
   - 对于尚未在战队内部技术评审中冻结的线协议、未标定的机械减速比、安装零位或保护动作阈值，必须先完成确认决策后再实现，切勿在代码里硬编码主观臆测的“魔数”。

## 2. 编码实现与离线验证闭环

在日常编码迭代中，我们遵循“修改代码 -> 本地快速构建 -> 跑通受影响契约测试”的高效循环。

### 对应不同改动的验证矩阵

| 代码修改类型 | 必须完成的最小验证要求 |
|---|---|
| **修改了设计与培训文档** | 检查 Markdown 链接有效性、代码块可编译性、API 与当前源码的一致性、命令参数正确性 |
| **修改了通用核心算法 / 通信协议** | 运行并全部通过 `core_contracts` 契约测试；若修改了边界条件，必须在测试文件中追加对应的极限测试或回归用例 |
| **修改了速度闭环 / 授权门逻辑** | 运行 `core_contracts` 与 `sil_contracts`，验证指令丢包、超时、恢复授权以及拒绝旧令牌的完整状态流转 |
| **修改了 STM32F407 适配 / 板级配置** | 执行 Arm GNU 交叉编译，运行 `check_firmware.py` 完成静态 ELF 符号安全审计，再申请安排板级实机观察 |

### 日常主机增量验证命令

当你已经完成了 [第一次构建与运行](../getting-started/第一次构建与运行.md) 的初始配置后，后续只需在工作区执行增量构建与测试：

```powershell
# 1. 调度 Ninja 进行增量编译（仅重新编译被修改的源文件及其依赖）
cmake --build build/host
if ($LASTEXITCODE -ne 0) { throw '主机增量编译失败，请根据上方编译器提示修正语法或类型错误' }

# 2. 执行 CTest 自动化测试套件
#    --test-dir build/host : 在指定的构建目录中执行测试
#    --output-on-failure   : 仅在断言失败时打印详细上下文，保持成功时的控制台输出简洁清爽
ctest --test-dir build/host --output-on-failure
if ($LASTEXITCODE -ne 0) { throw '契约测试未全部通过，请检查受影响组件的断言逻辑' }
```

> **小建议**：修复 Bug 后只需要重新跑受影响的测试，不需要每次文字小修改都把整个工程全部抹掉重新编译。修改 CMake 依赖项后按需重新配置；切换编译器时使用新的独立构建目录，保留原目录中需要的日志与轨迹。

## 3. 实机验收与安全防线 (需单独明确授权)

只有当离线测试与板级静态固件审计全部通过，且实车机械、电气准备就绪后，才可依据 [哨兵实施与验收](../robots/sentinel/实施与验收.md) 的规范流程逐步推进：

1. **S1 阶段（主控最小系统）**：隔离执行器，按实际 C 板版本、接口及探针手册核定主控独立供电方案，再验证时钟树、FreeRTOS 调度与 RAM 诊断。不能默认 Type-C 或 ST-Link 能给目标板供电，探针参考电压脚也不一定是供电输出。
2. **S2~S4 阶段（非运动观察固件）**：按各阶段验收规程隔离未测试执行器，验证 UART DMA 回显、DR16 分帧、CAN 接收与 BMI088 采样。真实电调反馈测试需要核定相应供电、机械固定与安全措施；不能一边要求电调完全断电，一边要求它产生反馈，也不能把 CAN 注入测试等同于实物反馈验收。
3. **动力测试与发弹阶段**：**必须经战队现场安全负责人单独明确授权**后方可开展！

> **极其重要的物理安全常识：概念不等价！**
> - **“无控制输出” $\neq$ “电机停止” $\neq$ “电机失能” $\neq$ “零电流” $\neq$ “保持姿态”**！
> - 例如：对于重力轴（如云台 Pitch 轴或挂载负载的升降机构），一旦电调直接断电、导致支撑力矩丧失，机械结构会在重力作用下瞬间砸落，造成严重损坏！应按该机构已确认的安全设计选择保持、机械制动或其他动作，不能在通用指南中默认确定；零电流命令与断电失能也不是同一个操作。
> - 编译成功和测试通过绝对不自动等同于获得了实机烧录与加电运行的许可！

## 4. 交付与代码提交规范 (Git Commit)

在准备将你的改动提交入库时，请养成良好的版本管理习惯：

1. **全面审查代码差异**：
   ```powershell
   git diff            # 审查所有已跟踪文件的局部改动
   git status --short  # 检查是否有意外新增的未跟踪文件（如临时日志、测试生成的 CSV 等）
   git diff --check    # 检查代码中是否存在行尾多余空白字符或合并冲突标记
   ```
2. **排除敏感与冗余文件**：
   - 确认没有将构建产物（`.elf`、`.bin`、`build/` 目录）、个人编辑器配置（`.vscode/` 局部文件）、敏感凭据密钥或超大二进制文件推送到 Git 中。
3. **遵循语义化提交规范**：
   - 提交信息推荐采用业界通用的前缀约定：
     - `feat:` 新增功能组件或模块
     - `fix:` 修复算法缺陷、边界条件或配置错误
     - `docs:` 完善文档、注释或使用指南
     - `test:` 补充单元测试或仿真用例
     - `refactor:` 在不改变外部行为的前提下重构内部代码
4. **明确事实与边界**：
   - 在提交信息或 Pull Request 中真实陈述已完成的验证（例如：“已通过主机契约测试与离线 ELF 静态检查”），未执行的实机项目切勿虚标为通过。

关于项目文档的规范与长期维护要求，请参考 [文档规范](../文档规范.md)。(^_^)v
