# 开发环境部署

刚进入战队的新队员往往还没有拿到 RoboMaster C 型开发板或实车硬件，但这完全不会阻碍你开始学习与编写代码！本项目支持在纯个人电脑（Windows PC）上完成核心数据结构、算法逻辑、单元测试与软件在环仿真（SIL）。因此，我们将环境部署划分为清晰的递进阶段：先装齐主机开发工具，就能立即跑通代码与核心测试。

Windows 主机已验证 MinGW GCC 14.2.0, 并新增 MSVC 19.51 (Visual Studio 2026) 的 Debug/Release 回归. 下文保留 MinGW 安装路线, 已有 MSVC 的成员也可使用第 2 节的独立构建方式. Linux/macOS 及其它组合尚未建立持续回归基线. 上位机与可复用台架脚本优先采用项目级 Python 环境, ARM 固件仍使用 Arm GNU 工具链.

## 1. 阶段化安装指南（按需搭建，不必一步到位）

| 阶段 | 所需工具 | 能在电脑上完成什么 |
|---|---|---|
| **第一阶段：主机核心开发** | PowerShell 7、Git、CMake、Ninja、MinGW-w64 C++ 编译器 (GCC 14.2.0) | 编译运行通用核心层代码、契约测试、主机示例与软件在环仿真 (SIL) |
| **第二阶段：板级交叉编译** | 追加 Python 3、Arm GNU Toolchain、完整 STM32CubeF4 1.28.3 SDK | 编译生成真实 C 板的 ELF/BIN/HEX 固件并执行离线符号审计（无需板卡硬件） |
| **第三阶段：外设配置修改** | 追加 STM32CubeMX 6.18.1 | 修改引脚分配、时钟树、DMA 通道并重新生成板级硬件代码 |
| **第四阶段：实机联调测试** | ST-Link 驱动、OpenOCD、GDB、串口调试工具（按需） | 获得实机操作授权后，进行硬件烧录、单步调试与在线观察 |

代码编辑器推荐使用 **VS Code**，并安装 `C/C++` 与 `CMake Tools` 插件。编辑器和知识库工具（如 Obsidian）仅为辅助工具，不是编译构建的前提条件。

## 2. 第一阶段：主机开发工具部署

下文中的路径均为推荐示例，你可以根据自己电脑的分区习惯存放，不必死板照搬原开发机的盘符。为了最大程度避免第三方开源脚本在 Windows 下的转义问题，强烈建议工具与工程目录使用**纯英文、无空格的简短路径**（但命令中对路径依然要规范添加双引号包裹）。

1. **PowerShell 7 (`pwsh`)**: 从 [Microsoft 官方文档](https://learn.microsoft.com/powershell/scripting/install/installing-powershell-on-windows) 下载安装。本项目所有的自动化构建与验证命令均基于现代 PowerShell 7。Windows 系统自带的 Windows PowerShell 5.1 内置语法和行为存在历史差异，请勿混淆使用。
2. **Git for Windows**: 从 [Git 官网](https://git-scm.com/download/win) 获取，安装时务必勾选将其添加到系统环境变量 PATH 中。换行符建议保持仓库默认配置，切勿在本地全局配置中强行批量改写所有文件的换行符（CRLF/LF）。
3. **CMake (>= 3.22)**: 从 [CMake 官方下载页](https://cmake.org/download/) 获取 Windows 64 位安装包，安装时选择将 CMake 添加到 PATH，或解压 ZIP 包后手动将其 `bin` 目录追加至 PATH。
4. **Ninja**: 高性能的现代构建工具。从 [Ninja Releases](https://github.com/ninja-build/ninja/releases) 下载 `ninja-win.zip`，解压得到 `ninja.exe`，并将其所在目录添加到 PATH 中。
5. **MinGW-w64 (GCC 14.2.0)**: 优先向维护者获取已验证 GCC 14.2.0 工具包的来源与安装方式，不预设队内网盘已有分发。若选择自行配置，推荐使用 [MSYS2](https://www.msys2.org/)。完成 MSYS2 基础安装与更新后，在 **MSYS2 UCRT64 终端**（注意：必须是 UCRT64 终端，UCRT 代表 Windows 现代标准 C 运行库，比旧版 MSVCRT 拥有更好的规范兼容性）中执行：

```sh
# 在 MSYS2 UCRT64 环境下安装原生 64 位 GCC 编译工具链
pacman -S mingw-w64-ucrt-x86_64-gcc
```

MSYS2 在线仓库可能提供不同 GCC 版本，安装后记录实际版本并通过项目测试，不能默认等同于已验证基线。安装完成后，将 MSYS2 安装根目录下的 `ucrt64/bin` 路径加入 Windows 用户环境变量 PATH。**切勿使用 MSYS2 根目录 `usr/bin` 下的 GCC**，那是为模拟 POSIX 环境设计的模拟层编译器，无法替代 Windows 原生 MinGW 工具链。此外，编译器 `bin` 目录中附带的基础运行库 DLL（如 `libstdc++-6.dll`、`libgcc_s_seh-1.dll`）是程序运行所必需的，千万不能只把 `g++.exe` 单独拷出来使用。

### 环境变量 PATH 配置与自检

建议通过 Windows 系统的“编辑系统环境变量”或“编辑账户的环境变量”面板，在用户级 `Path` 中追加上述工具路径（修改用户变量无需管理员权限）。**注意：修改环境变量后，必须完全重启终端窗口与 VS Code，新的 PATH 才会生效**。

你可以打开一个全新的 PowerShell 7 终端，逐行执行以下自检脚本：

```powershell
# -----------------------------------------------------------------------------
# 临时环境变量调试示例（可选）:
# 如果你在不同目录安装了工具，可临时在当前终端会话将工具目录前置，不影响全局系统
# $env:PATH = "C:/msys64/ucrt64/bin;$env:PATH"
# -----------------------------------------------------------------------------

# 1. 检查 PowerShell 版本（主版本号 Major 必须为 7，确认不是系统自带的 5.1）
$PSVersionTable.PSVersion

# 2. 检查关键工具的实际定位路径，确认没有被其他环境（如旧版 MinGW、Strawberry Perl 等）意外劫持
Get-Command git, cmake, ninja, gcc, g++ | Select-Object Name, Source

# 3. 打印各工具的版本信息，确认均可正常唤起并满足版本要求
git --version     # Git 分布式版本控制
cmake --version   # 构建配置工具（要求 >= 3.22）
ninja --version   # 底层构建工具
g++ --version     # C++ 编译器（队内验证基线为 GCC 14.2.0）
```

自检标准：全部命令均能正确输出版本号；`g++` 必须来自预期的 MinGW 工具链。如果你电脑上安装了多个编译器，可以使用 Windows 自带的 `where.exe g++` 查看各路径的查找优先级顺序（在 PowerShell 中注意要打全 `where.exe`，因为单独的 `where` 是 PowerShell 内置 cmdlet `Where-Object` 的简写别名）。

自检全部通过后，就可以立即前往 [第一次构建与运行](第一次构建与运行.md) 体验编译与测试了！(￣▽￣)／

### 可选 MSVC 主机构建

已验证 Visual Studio 2026 的 C++ 工具集 MSVC 19.51、Windows SDK 10.0.26100 和 CMake 4.4. 安装 Visual Studio 时选择“使用 C++ 的桌面开发”及 Windows SDK; 不需要因此更改现有 MinGW 缓存. 新建独立构建目录:

```powershell
cmake -S . -B build/host-msvc -G "Visual Studio 18 2026" -A x64
cmake --build build/host-msvc --config Debug
ctest --test-dir build/host-msvc -C Debug --output-on-failure
# Release 由同一多配置生成器单独生成
cmake --build build/host-msvc --config Release
ctest --test-dir build/host-msvc -C Release --output-on-failure
```

使用上述生成器需安装匹配的 Visual Studio 和支持它的 CMake; `cmake --help` 可检查生成器名称. 不将旧版 CMake 的最低要求 3.22 当作支持所有新生成器的保证. 工程已为 MSVC 配置 `/utf-8`, 不要为修复系统代码页问题批量改写中文注释. 若安全软件隔离产物, 先核对日志、来源与源码, 不关闭防护或排除整个仓库.

## 3. 第二阶段：板级交叉编译工具链

当你准备编译可运行在 STM32 单片机上的固件，或者参与板级驱动离线审计时，才需要部署本阶段工具。

### Python 3 解释器

上位机脚本使用仓库根目录 `.venv/`, 依赖清单为 `requirements-dev.txt`. 建立与使用方式集中见 [串口观测与应用接入](../guides/串口观测与应用接入.md), 无需全局安装依赖; 只运行观察器不要求安装 Arm/Cube 工具链.

从 [Python 官网](https://www.python.org/downloads/windows/) 下载并安装 Python 3（建议 3.10 或更高版本），安装向导第一页务必勾选 **“Add python.exe to PATH”**。我们的离线固件静态分析脚本（如符号审计、安全门符号检查）仅使用 Python 标准库，不需要安装额外的第三方包。安装后运行 `python --version`，确认能正确显示版本，且没有弹出 Windows 微软应用商店的快捷方式重定向。

### Arm GNU Toolchain (交叉编译器)

因为我们的 PC 是 x86_64 架构，而车载主控板是 ARM Cortex-M4 架构，所以必须使用交叉编译器。
请从 [Arm 开发者下载页面](https://developer.arm.com/downloads/-/arm-gnu-toolchain-downloads) 下载面向 Windows 主机的 **`arm-none-eabi`** 预编译包：
- **目标体系说明**：`arm` 代表目标架构为 32 位 ARM；`none` 代表目标平台无操作系统/裸机运行环境（区别于 Linux 系统的板卡）；`eabi` 代表遵循嵌入式二进制接口规范。千万不要错误下载面向 64 位 Linux 的 `aarch64-linux-gnu` 工具包。
- **验证版本**：队内当前基线为 **14.2.Rel1**（编译器执行报告为 `14.2.1`）。

下载 ZIP 压缩包后完整解压到你的工具目录（例如 `C:/Tools/arm-gnu-toolchain-14.2.rel1`）。你可以将其中的 `bin` 目录加入系统 PATH，也可以在板级 CMake 构建命令中通过 `-DARM_GNU_ROOT=...` 显式传参。请保留压缩包中自带的所有调试与分析工具（如 `arm-none-eabi-nm.exe`、`arm-none-eabi-gdb.exe`、`arm-none-eabi-objcopy.exe`），后续离线固件检查脚本会直接使用它们。

### STM32CubeF4 官方底层 SDK

从 [ST 官网 STM32CubeF4 页面](https://www.st.com/en/embedded-software/stm32cubef4.html) 或 STM32CubeMX 内置的包管理器下载 **完整的 STM32CubeF4 1.28.3 固件包**。
- **注意更新陷阱**：如果你从官网下载的是增量补丁压缩包，必须严格按照 ST 官方流程在 1.28.0 基础包上完成升级安装；切不可把单独的补丁目录或未打补丁的 1.28.0 基础包直接当成 1.28.3 传给构建系统。
- **目录结构校验**：SDK 根目录下必须存在 `package.xml`、`Drivers/`、`Middlewares/` 等核心子目录。
- **元数据校验**：为了核对预期包版本，`boards/sentinel_f407/sdk.cmake` 锁定了官方 SDK `package.xml` 的 SHA256 哈希值。如果构建时报错提示 SDK 校验失败，说明 SDK 文件损坏或版本不符，请重新检查安装包，**不能为了绕过错误而删除或修改哈希校验**。元数据匹配不等于整个 SDK 每个文件都已验证完整。

板级构建时，CMake 参数名为 **`-DEC_STM32CUBE_F4_ROOT`**。项目设计上不会自动隐式读取同名环境变量，必须在构建命令中显式指定路径，详见 [板级构建说明](../boards/sentinel_f407/生成与构建.md)。

```powershell
# 交叉编译工具链自检示例
python --version

# 如果已将 Arm 工具链的 bin 目录加入 PATH，可直接执行：
arm-none-eabi-gcc --version  # 查看 ARM 交叉编译器版本（应显示 14.2.1）
arm-none-eabi-nm --version   # 查看目标文件符号分析工具版本
```

## 4. 第三阶段：STM32CubeMX (仅重新配置外设硬件时需要)

从 [ST 官网](https://www.st.com/en/development-tools/stm32cubemx.html) 安装 STM32CubeMX。当前我们使用的工程基线版本为 **6.18.1**，不要使用旧版生成器。

**重要认知**：
仓库源码中已经包含了预先生成好的完整板级外设代码！如果只是拉取代码、阅读、编译和烧录固件，**根本不需要安装或运行 STM32CubeMX**。只有当你需要重新分配引脚、调整系统时钟分频、修改 DMA 流分配时，才需要运行自动化脚本唤起 CubeMX。重新生成代码会覆盖板级生成目录，操作前必须做好 Git 暂存并阅读 [板级生成与构建](../boards/sentinel_f407/生成与构建.md)。

## 5. 第四阶段：实机联调工具 (按需准备，注意安全)

实机调试工具在硬件就绪且获得单独授权后使用：
- **ST-Link 调试器驱动**: 推荐安装官方 [STSW-LINK009 驱动](https://www.st.com/en/development-tools/stsw-link009.html)。连接板卡前务必使用万用表核对调试接口线序（SWCLK、SWDIO、GND）与目标参考电压（3.3V），防止接反烧毁元器件。
- **OpenOCD**: 从开源社区获取支持 Windows 的预编译版本。本项目验收脚本要求 OpenOCD 必须支持 `dapdirect_swd` 传输协议，并在执行前核验 `openocd --version` 以及脚本中指定的 `interface/stlink.cfg` 和 `target/stm32f4x.cfg` 文件是否存在。
- **GDB 调试器**: 直接使用 Arm GNU Toolchain 中自带的 `arm-none-eabi-gdb.exe` 即可。
- **串口观察工具**: 仓库内置了 Python 串口回显测试脚本 `boards/sentinel_f407/tools/uart_probe.py`，它依赖 `pyserial`。建议在独立的 Python 虚拟环境中安装依赖。

**特别提醒**：即便所有实机工具均已安装就绪，未经安全确认与明确授权，严禁擅自给动力板上电或执行电机转动命令！具体流程必须严格遵循 [哨兵实施与验收](../robots/sentinel/实施与验收.md)。

## 6. 新手常见环境排错速查

- **终端提示找不到程序或命令**:
  - 原因：安装后未重启终端，或者环境变量 PATH 中填写的路径有误（注意 PATH 应指向包含 `.exe` 的 `bin` 目录，而不是其父目录）。
  - 排查：打开全新的 PowerShell 7 窗口，使用 `Get-Command <工具名>` 检查命令的实际解析位置。
- **编译成功但程序运行时闪退报错（例如提示缺少某 DLL）**:
  - 原因：Windows 缺少 MinGW 的 C++ 标准运行库。
  - 排查：检查 MinGW 的 `bin` 目录是否仍然保留在 PATH 中，确保程序启动时能找到同目录下的 `libstdc++-6.dll` 等依赖库；不要把不同来源的 MinGW DLL 混杂在一起。
- **修改了编译选项后，CMake 依然固执地使用旧编译器**:
  - 原因：CMake 在首次配置时会把编译器路径永久保存在 `CMakeCache.txt` 缓存中。
  - 解决：使用新的独立目录重新执行 cmake 配置命令，并同步修改后续构建/测试的目录参数，保留旧目录中的必要证据；切勿在同一个构建目录中混用主机编译器与 Arm 交叉编译器。
- **CMake 提示 `Unexpected CubeF4 package metadata`**:
  - 原因：指定的目录不是纯正完整的 STM32CubeF4 1.28.3 官方发布包（例如误指向了补丁包解压的中间目录或旧版 1.28.0 文件夹）。
  - 解决：核对 SDK 根目录下的 `package.xml` 内容，确保版本号与哈希完全吻合。
