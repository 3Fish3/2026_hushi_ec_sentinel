# 第一次构建与运行

前置条件: 已按 [环境部署](环境部署.md) 装好第一阶段的主机开发工具。
以下所有操作均在 **PowerShell 7 终端、仓库根目录**下执行，整个过程不需要连接任何单片机、调试器或电机！(^_^)v

## 1. 获取项目源码

请向战队代码维护者获取真实的 Git 仓库地址与拉取权限。请将下方脚本中的占位符替换为真实 URL 后执行克隆：

```powershell
# 1. 填入战队内部仓库地址并克隆工程
$repoUrl = '替换为维护者提供的仓库地址'
git clone $repoUrl Hushi_EC_2026_Refactor
if ($LASTEXITCODE -ne 0) { throw 'Git 克隆失败，请检查网络与仓库权限' }

# 2. 进入包含根目录 CMakeLists.txt 的工程工作区
Set-Location Hushi_EC_2026_Refactor
```

若你已经从本地或内网取得了完整的工作树，直接通过 `cd` 进入包含根目录 `CMakeLists.txt` 的项目文件夹即可。主机学习与测试完全自包含在代码仓库中，不需要旧工程目录、机械三维 CAD 文件或外部资料。

## 2. 编译、构建与运行主机单元测试

我们将构建产物放在 `build/host` 独立目录中，保持源码树干净整洁：

```powershell
# 遇到未捕获的异常立即终止执行
$ErrorActionPreference = 'Stop'

# 1. 使用 CMake 生成基于 Ninja 构建器的工程配置
#    -S .                    : 指定源码根目录为当前工作区
#    -B build/host           : 指定构建产物存放于 build/host 目录
#    -G Ninja                : 使用高性能构建工具 Ninja 作为生成器
#    -DCMAKE_BUILD_TYPE=Debug: 生成携带完整调试信息的 Debug 目标
#    -DCMAKE_C_COMPILER=gcc  : 显式指定 C 编译器为 MinGW gcc（防止误选系统其他编译器）
#    -DCMAKE_CXX_COMPILER=g++: 显式指定 C++ 编译器为 MinGW g++
cmake -S . -B build/host -G Ninja -DCMAKE_BUILD_TYPE=Debug `
  -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++
if ($LASTEXITCODE -ne 0) { throw 'CMake 配置生成失败，请检查 MinGW 工具链与路径' }

# 2. 调度 Ninja 并行编译所有核心库、测试用例与示例程序
cmake --build build/host
if ($LASTEXITCODE -ne 0) { throw '源码编译失败，请根据上方终端输出定位错误' }

# 3. 运行 CTest 自动化测试套件
#    --test-dir build/host   : 指向测试目标所在的构建目录
#    --output-on-failure     : 如果测试未通过，立即打印详细失败断言与控制台输出
ctest --test-dir build/host --output-on-failure
if ($LASTEXITCODE -ne 0) { throw '测试套件未全部通过' }
```

> **参数说明小贴士**：
> 显式指定 `-DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++` 可以避免 CMake 在拥有多个编译器的电脑上意外抓取到 Visual Studio 或其他架构的编译器。
> 在 PowerShell 中，外部程序（如 `cmake`、`git`）即使返回非零错误码也不会默认触发 PowerShell 异常，因此我们在关键步骤后通过 `if ($LASTEXITCODE -ne 0)` 严格拦截错误。

构建与测试完成后，终端应当报告 `100% tests passed`。默认有五项 C++ 测试; CMake 找到 Python 时增加两项客户端/跨语言测试, 共七项. 电机客户端测试需项目 Python 依赖及 Tk, 缺少模块时会报告跳过, 不等于通过：

| 测试名称 | 验证的核心内容 |
|---|---|
| **`core_contracts`** | 32 位时间回绕处理、进程内同步通道（邮箱/快照/事件队列）、代次授权门、PID 算法运算、DR16/DJI 协议编解码等基础契约 |
| **`sil_contracts`** | 软件在环模拟：虚拟电机闭环控制、指令丢包超时失效、断电急停后旧授权拒绝、UART 与 IMU 输入流离线回放 |
| **`gm6020_bench_contracts`** | 台架控制、目标与生命周期、虚拟被控对象检查; 不证明实物已调好 |
| **`motor_bench_client_contracts`** | Python 假串口与跨语言编码检查, 不操作硬件 |
| **`uart_frame_contracts`** | 有界串口分帧、CRC、错误重同步和观测字段编码 |
| **`board_monitor_contracts`** | Python 可用时执行: 与 C++ 向量对照、过期显示、只读请求及端口清理 |
| **`assembly_example`** | 完整组件组装范例：验证目标过期自动失效、重新授权后拒绝跨代次旧命令等关键安全特性 |

所有生成的可执行文件均位于 `build/host/` 目录下。如果你想观察完整的组件拼装与运行日志，可以直接手动执行：
```powershell
./build/host/ec_assembly_example.exe
```
终端将输出 `assembly: valid command executed; expiry and old grant rejected`，证明核心逻辑已按预期完成拦截与流转！

> **需要编译 Release 优化版本？**
> 将上述命令中的构建目录改为 `build/host-release`，构建类型参数改为 `-DCMAKE_BUILD_TYPE=Release`，对新目录独立运行配置与编译即可。**绝对不要在同一个目录中交替混合 Debug/Release 或主机/ARM 交叉编译！**

## 3. 运行软件在环仿真 (SIL), 导出仿真轨迹

很多新队员会好奇：“我们在电脑上既没有接电机，也没有装陀螺仪，控制算法是怎么验证的呢？”
答案就是 **软件在环（Software-in-the-Loop, SIL）**！
在 SIL 测试中，核心控制算法、授权状态机和通信编解码全部使用真实代码，但时钟、CAN 总线和电机物理响应是由测试夹具中的数学模型模拟的一阶惯性系统。

你可以运行测试程序并生成仿真轨迹文件：

```powershell
# 运行 SIL 软件在环测试，并导出指定场景的时间-响应轨迹数据到 CSV 文件
# 注意: 目标 CSV 路径必须是一个尚不存在的文件; 为防止覆盖有价值的历史验收记录，程序已存在同名文件时会拒绝覆盖
./build/host/ec_sil_tests.exe --csv build/host/trace.csv
if ($LASTEXITCODE -ne 0) { throw 'SIL 软件在环测试执行失败' }
```

生成完成后，你可以使用 VS Code 的表格插件、Excel 或 Python 打开 `build/host/trace.csv` 进行观察与绘图分析。阅读轨迹数据时需要注意以下科学事实：
- **按 `scenario`（场景）独立阅读**：文件中包含了多个不同的测试工况（如正常阶跃响应、指令超时丢包响应、授权失效急停响应等），它们是彼此独立的模拟，不能把不同场景混在同一条时间线上绘制。
- **`elapsed_ms`**：测试夹具内部的虚拟仿真时间轴，单位是毫秒。
- **`model_speed_rad_s`**：虚拟一阶电机模型当前的理论物理转速（单位为国际标准单位 rad/s），它反映被控对象受力加速的过程。
- **`feedback_rad_s` 与 `feedback_fresh`**：电调反馈回来的转速读数；必须配合 `feedback_fresh`（是否新鲜）一起判断——在没有新鲜反馈时，占位数据不可当作电机的真实速度。
- **`output_valid`**：仅代表当前周期的控制器计算出了合法的输出值，并不代表底层 CAN 已经发到线路上，更不代表电机物理上已经转动。
- **`status` 与 `tx_result`**：导出的列是状态枚举的**整数值**（例如 `VelocityStatus` 与 `SendResult` 的底层枚举数值），而非长字符串，不是已冻结的长期线协议。

模型参数是虚构值，不是实车参数识别结果；PC 命令源采用进程内类型接口，尚不是正式上位机线协议。`accepted` 后丢包也不一定可检测。`build/` 不纳入 Git，需要长期保留的轨迹应另行保存。

> 完整的仿真边界与说明请参考 [SIL 验证边界](../robots/sentinel/实施与验收.md#21-无硬件阶段的软件在环验证-sil)。需要铭记：软件在环测试可以发现已覆盖场景中的逻辑错误，没有可保证的缺陷检出比例，但它绝不能替代实机上的机械惯量、发热堵转与电气抖动验证。

## 4. 学习路线下一步建议

完成了第一次编译与测试，恭喜你已经成功迈出了第一步！(￣▽￣*)
接下来你可以按如下顺序继续深入：
1. **建立代码分层直觉**：阅读 [项目分层与代码导航](../guides/项目分层与代码导航.md)，理解通用核心、平台适配与板级驱动的边界。
2. **掌握 C++ 实用特性**：如果不熟悉现代 C++ 规范，阅读 [从 C 到现代 C++ 入门](../guides/从C到现代C++入门.md)。
3. **按模块逐个攻克**：从 [核心通道](../modules/core/通道与数据交换.md)、[时间与时效](../modules/core/时间与时效.md)、[执行授权门](../modules/core/授权门.md) 到 [PID 控制器](../modules/control/PID.md)。
4. **编译真实板级固件**：当第二阶段的 ARM 工具链装好后，前往 [板级生成与构建](../boards/sentinel_f407/生成与构建.md) 体验编译出第一份 `.hex` 固件！

## 5. 新手常见构建问题排查

- **CMake 报错 “Ninja was not found in PATH” 或 “CMAKE_C_COMPILER not found”**：
  - 请使用 `Get-Command ninja, gcc, g++` 检查环境变量；如果是在打开终端后才安装的工具，必须关闭终端并重启。
- **CMake 选中的编译器不是刚刚安装的 MinGW GCC**：
  - 改用新的独立构建目录，并在配置、构建和测试命令中同步替换目录名，显式传入 `-DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++`。保留原目录中需要的固件、日志和 CSV，不要删除整个 `build/`。
- **测试运行时报错或断言失败**：
  - 检查终端中输出来的第一个失败断言信息。注意区分是操作系统层面的权限或动态库缺失，还是算法断言未通过；不要在未查明根因的情况下随意修改测试断言阈值。
- **提示 CSV 文件已存在导致导出失败**：
  - 将 `--csv` 参数指定为一个新的文件名（例如 `build/host/trace_run2.csv`），或者在确认不需要旧记录后手动删除旧的 CSV 文件。
