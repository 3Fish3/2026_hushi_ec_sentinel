# 时间与时效 (Time & TTL)

源码: [time.hpp](../../../include/ec/time.hpp)，核心类型位于 `ec` 命名空间。对应契约测试: `tests/core_tests.cpp` 中的 `time_contracts`。

## 1. 为什么“收到过数据”不等于“数据现在还能用”？

在机器人系统中，通信掉线是家常便饭（例如遥控器距离过远、上位机视觉卡顿、CAN 报文受到电机大电流干扰等）。
如果控制算法在没有收到新数据时，继续使用上一次收到的速度目标，机器人就会像“无头苍蝇”一样维持原速狂奔，直接发生撞墙甚至炸场！

因此，系统内的每一份数据，除了数值本身，都必须明确回答两个关键问题：
1. **这是什么时候的数据？**（采样时刻戳）
2. **这组数据最长允许被信任多久？**（时效期 TTL，Time-To-Live）

为了防止代码中错误地把“绝对时间点（Tick）”与“相对时间间隔（Lifetime）”混淆运算，我们使用了强类型包装：

| 强类型名称 | 物理语义 | 内部实现与数值范围 |
|---|---|---|
| **`Tick`** | 单调毫秒时间戳 | 32 位无符号整型 (`std::uint32_t`)，每毫秒加 1，约 49.7 天发生一次无符号自然回绕 |
| **`Lifetime`** | 有效生命期 (TTL) | 必须满足：大于 0 且小于半个回绕周期（即 $0 < \text{ms} < 2^{31}$，约 24.8 天） |
| **`Sample<T>`** | 携带元数据的样本结构体 | 包含三个成员：数值 `value`、采样时刻 `sampled_at`、有效性 `validity` |
| **`Validity`** | 样本有效性枚举 | `unknown`（未初始化/未知）、`valid`（正常有效）、`invalid`（传感器异常/校验失败） |

## 2. 模块职责与边界

- **纯逻辑与算法**：本模块只负责时间差计算、超时判断与回绕算法，**不负责读取硬件定时器**。
- **本地单调时钟域**：`Tick` 的来源是本地 MCU 持续运行的单调定时器（如 HAL tick）。外部上位机（如 Jetson）发来的时间戳不可在未经协议同步的情况下直接与 MCU 本地 `Tick` 比较。
- **MCU 重启语义**：MCU 一旦复位重启，本地时基清零，必须同步清空所有历史通道中的数据与会话状态。

## 3. 主机可运行示例

下面的代码演示了样本的时效校验规则，以及核心算法是如何优雅处理 32 位定时器回绕的：

```cpp
#include "ec/time.hpp"
#include <iostream>

// 主机可运行示例: 演示 Sample 时效判定与 32 位整数溢出回绕处理
int main() {
    // 1. 构造一个在 100 ms 时刻采集到的电机转速样本 (2.0 rad/s)
    ec::Sample<float> speed{
        2.0f,                   // 物理数值: 2.0 rad/s
        ec::Tick{100},          // 采样时刻: 100 ms
        ec::Validity::valid     // 状态: 有效
    };

    // 2. 正常时效测试 (设定 TTL 有效期为 10 ms):
    //    当前时刻为 109 ms，时间差 = 109 - 100 = 9 ms < 10 ms，数据依然新鲜！
    if (!speed.fresh_at(ec::Tick{109}, ec::Lifetime{10})) {
        return 1; // 应该新鲜，若判定不新鲜则失败
    }

    // 3. 到期边界测试:
    //    当前时刻为 110 ms，时间差 = 110 - 100 = 10 ms。
    //    核心设计契约：当流逝时间严格等于或超过 TTL 时，瞬间失效判定（严格小于）！
    if (speed.fresh_at(ec::Tick{110}, ec::Lifetime{10})) {
        return 2; // 此时应该已过期，若仍判定新鲜则失败
    }

    // 4. 奇妙的 32 位回绕测试 (Unsigned Overflow Wrap-Around):
    //    假设数据在定时器溢出前夕 0xFFFFFFFEu (即 4294967294 ms) 采样，
    //    而当前时刻已经跨越回绕点，来到了系统计数的第 2 ms (即 0x00000002u)。
    //    无符号减法在二进制补码下: 2u - 0xFFFFFFFEu = 4u！
    //    由于 4 ms < 5 ms (TTL)，算法能丝滑且准确地判定该跨越回绕的数据依然有效！
    if (!ec::fresh(ec::Tick{2}, ec::Tick{0xfffffffeu}, ec::Lifetime{5})) {
        return 3; // 溢出回绕处理失败
    }

    return 0; // 全部契约验证通过
}
```

## 4. 核心数学原理：为什么不需要写复杂的 `if (now < received)`？

很多嵌入式新手在处理 32 位定时器溢出时，都会写一堆复杂易错的 `if-else` 条件去判断当前计数是否小于上次计数。

在 C++ 中，**无符号整数的减法是严格定义为模 $2^{32}$ 运算的**。
以单字节 8 位无符号数（最大值 255）为例：
- 假设采样时刻是 254，当前时刻回绕到了 2。
- 计算无符号差值：`(uint8_t)(2 - 254) = (uint8_t)(-252) = 4`！
- 算出的差值正好是物理上流逝的 4 个 tick！

只要我们保证**数据的观察周期在半个回绕周期（约 24.8 天）之内**，这个无符号差值就能始终精确反映时间的物理流逝。
这也意味着：单看 `now.ms < received.ms` 并不代表系统时间“倒流”了，它完全可能是正常的自然回绕。我们设计的 `fresh()` 算法天然免疫此问题！

## 5. 常见调用误用

1. **没有新数据时，为了让下游继续工作，定期更新旧样本的 `sampled_at` 为“当前时间”**：
   - 危害：这会彻底瘫痪掉线保护机制！当下位机与上位机断链时，机器人将无法识别出故障，丧失急停能力。
2. **直接比较两个来自不同时钟源的 `Tick`**：
   - 外部传感器（如带独立时间戳的高精度外部 IMU）必须在进入本层之前，由接收驱动转换映射到本地单调时钟域。
