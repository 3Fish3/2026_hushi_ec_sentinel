# 周期规划 (Periodic Scheduling)

源码: [periodic.hpp](../../../include/ec/periodic.hpp)，函数位于 `ec` 命名空间。对应契约测试: `tests/core_tests.cpp` 中的 `periodic_contracts`。

## 1. 为什么不能简单地“计算完成后延时固定时长”？

很多初学者写单片机控制任务时，喜欢这么写：
```c
void ControlTask(void* argument) {
    while (1) {
        do_pid_calculation(); // 假设本次计算耗时 2 ms
        vTaskDelay(10);       // 延时 10 ms
    }
}
```
**这种写法会带来致命的“周期相位累积漂移”！**
因为两次任务启动的实际间隔是 `2 ms (计算耗时) + 10 ms (延时) = 12 ms`，而不是期望的 10 ms！
在 1000 个周期后，控制任务就会落后足足 2 秒！这会导致基于固定采样时间 $dt$ 的微分项与积分项计算出现严重失真，极易诱发系统振荡。

为了消除这种累积误差，必须采用 **“绝对固定网格基点调度”**：
无论单次计算耗时多长，下一次唤醒的时刻必须锚定在固定的时间网格上（如 100ms, 110ms, 120ms, 130ms...）。

## 2. 发生严重卡顿与调度超时时，该怎么办？

设想如果某次中断或高优先级任务抢占了 CPU，导致控制任务从 100 ms 一直被阻塞到了 135 ms 才被调度：
- 此时如果机械地补齐所有错过的周期，任务就会连续密集突发执行 3 次，霸占 CPU 并造成严重的执行震荡。
- 本项目设计的纯规划函数 `plan_periodic(previous, now, period)` 能够以常数时间复杂度直接将时间锚点平移到最近的网格，**并明确告诉你中途错过了多少个周期（`skipped`）**，让应用层决定是记录警告还是触发降级保护，绝不盲目补跑失效的陈旧周期。

## 3. 主机可运行示例

下面的示例演示了 `plan_periodic` 在发生严重超时时的优雅对齐与漏周期统计能力：

```cpp
#include "ec/periodic.hpp"
#include <iostream>

// 主机可运行示例: 演示周期时间网格规划与超时跳步 (Skip) 计算
int main() {
    // 参数说明:
    // previous = 100 ms (上一个周期的调度锚点)
    // now      = 135 ms (当前实际被唤醒的时刻，显然被其他高优先级任务卡顿阻滞了)
    // period   = 10 ms  (期望的控制周期为 10 ms)
    const auto plan = ec::plan_periodic(100, 135, 10);

    // 1. 检查规划是否合法 (若入参 period <= 0 或两次观察超过半个回绕周期，返回 std::nullopt)
    if (!plan) {
        return 1; // 参数非法
    }

    // 2. 核心数学对齐契约验证:
    //    - 理论网格时刻本应是 110, 120, 130, 140...
    //    - 当前时间是 135 ms，说明 110, 120, 130 这 3 个周期的截止点已经全部过去！
    //    - plan->anchor_tick: 调整后的最新锚点平移为 130 ms
    //    - 下一次预期的执行截止点将自动对齐为: anchor_tick + period = 130 + 10 = 140 ms！
    //    - plan->skipped: 明确报告跳过了 3 个旧周期，方便上层安全状态机做超时诊断
    if (plan->anchor_tick == 130 && plan->skipped == 3) {
        return 0; // 规划与对齐完全符合预期！
    }

    return 2;
}
```

## 4. 平台落地与调用注意事项

- **纯规划 vs 真正等待**：`plan_periodic` 是一个纯数学规划函数，不包含操作系统级别的挂起或睡眠。在 STM32 平台上，由平台层的 `PeriodicWait` 负责调用 FreeRTOS 的 `vTaskDelayUntil` 完成真正的硬件阻塞休眠（详见 [STM32F407 平台适配](../../platforms/stm32f407.md)）。
- **零漂移 $\neq$ 零抖动**：虽然基点规划彻底消除了累积时钟漂移，但在实时操作系统中，由于硬件中断嵌套与高优先级任务抢占，每次被唤醒的微秒级时刻依然存在轻微抖动。因此，PID 计算时推荐传入实际采集到的流逝秒数 `dt_s`，而不是粗暴假定每周期绝对丝毫不差。
